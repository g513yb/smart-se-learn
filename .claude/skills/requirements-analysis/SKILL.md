# 需求分析

## 概述

把原始信息变成可开发、可验收、可追溯的需求条目。核心原则：**只记录有来源的内容；没有来源的，变成问题，不变成需求。**

## 边界

- 在内：采集、故事卡、验收标准、优先级、建模、评审、变更记录
- 在外：实现、测试执行、用户签收

## 硬规则

1. **来源与问题标签**：每条需求必须有来源，只能是 `S-`（用户陈述/原话）、`D-`（明确决策）、`R-`（既有文档）。`Q-` 是缺口问题，不是来源；`P-` 是实践参考，只能生成 Q；`I-` 是推断，不得进入“已确认”。引用 P 的需求必须另有 S/D/R。
2. **先提问后动笔**：成形前先列缺口；缺口未确认，不写完整需求。
3. **未知入清单**：不确定项写入 `docs/requirements/07-dialogue.md` 的 Q 表，编号并指派确认人，不留在正文里当假设。
4. **示例保护**：出现“比如 / 例如 / 类似”时，先确认是举例还是真实需求；举例不得直接升级为需求。
5. **禁止越界**：不自行添加未提及的角色、字段、业务规则、非功能指标、技术方案。
6. **确认权在人**：AI 不得把需求标为“已确认”。任一成员可确认任意需求；记录确认人和日期。确认不等于评审，评审由另一人执行。
7. **设计隔离**：需求只写“做什么、为什么”；技术方案、算法、架构、库选型写入 `docs/design-notes.md`（`DSN-`），不进入需求文档。
8. **主动发现必有依据**：AI 主动提出的需求候选必须引用 `P/S/D/R`，并关联对应的 Q；没有依据的只能作为开放问题，不得写成需求候选。
9. **整理不等于补全**：把用户原话整理成故事卡时，只能重述、拆分、归一化用语；不得补充原话中没有的角色、字段、规则、指标。缺的字段写成 Q 或“未决问题”，不写成内容。
10. **知识回填**：Q 被回答后，把回答记为 S-xxx；稳定的业务事实写入 `context.md`，术语写入 `glossary.md`。回答不得只停留在问答记录里。
11. **冲突检查必做**：新增需求、变更需求、转为“已确认”前，按 `references/conflict-check.md` 检查并记录结论；不得把“未发现”写成“没有冲突”。
12. **基线变更由人确认**：项目基线（愿景、范围、非目标、角色）的修改，由任一成员一人确认；记录 `D`（确认人姓名、日期）和 `06-changes.md` 的 CR；初次建立记 D、不建 CR；另一人评审；AI 不得自行修改。`CLAUDE.md` 和 skill 的管理/流程规则变更记录在文件本身，不写项目 D/CR。临时规则：当前文件存储无应用层，暂不要求两人会签。愿景细则见 `references/vision-guide.md`。
13. **文档边界**：需求文档只放标题、指针、表头和项目内容；流程、管理、确认、评审规则只放 `CLAUDE.md` 和 skill references。需求文档里出现规则文字，视为缺陷：移到 skill，不在原处新增。
14. **管理文件边界**：管理文件只写结构、字段、含义、规则和通用示例；项目概念、事实、需求和具体角色只写项目文件。示例必须通用，或明确标注“非本项目”。

违反字面规则即违反规则本意。

## 红旗：出现即停止

- “为了完整，先合理补全”
- “这是行业常见做法”
- “用户应该会需要”
- “先假设，后面再确认”
- “写细一点更专业”
- “两句话就能推出这些需求”
- “把推断写进‘以便’从句”
- “在验收标准的前置条件里补假设”
- “系统采用 / 通过算法 / 使用某框架”
- “对标平台这么做，所以我们也这么做”
- “我觉得应该有，但说不出依据”

处理方式：把内容改写成 `Q-` 问题，写入问答记录，等确认后再写需求。

## 会话开始

读 `CLAUDE.md`、`docs/team.md`、`docs/STATUS.md`、`00-vision.md`、`context.md`、`glossary.md`、当前模块 brief、`07-dialogue.md`（S 与 Q）和 `08-decisions.md`（D），用 3～5 行复述当前理解。

- 项目文件缺失时：先按下一节“初始化”建立，不凭记忆补，不跳到模块选择。
- 未指定模块：列出 `00-vision.md` 中已确认的模块清单，参考 `STATUS.md` 的下一步，请用户选择；不得自行开始。
- 已指定模块：把模块选择记为 `S-xxx`，进入 1.0。

## 初始化：从零建立

适用：会话开始时项目文件缺失，或用户要求从零建立。初始化只建立结构、团队信息和项目状态，不写需求、假设、NFR 或验收标准。

1. **检查**：按 `references/file-templates.md` 的文件清单逐项检查，列出存在与缺失；不把缺失当已知，不预建空文件。
2. **团队与分工**：问清成员、各自负责范围、确认与评审关系。AI 起草 `docs/team.md`，任一成员确认后写入，确认人和日期写在文件内；不写项目 D/CR，不记需求 S。
3. **项目状态**：AI 根据已存在文件提议当前阶段（全新项目默认“需求分析尚未开始”）、下一步、迭代节奏和待决事项；任一成员确认后，按 `file-templates.md` 创建或更新 `docs/STATUS.md`，确认人和日期写在文件内；不写项目 D/CR。
4. **愿景**：按 `references/vision-guide.md` 第 4 节初次建立。回答先记 `S`；第一次需要 `S` 时按 `file-templates.md` 创建 `07-dialogue.md`，第一次需要 `D` 时创建 `08-decisions.md`。
5. **角色**：按 `references/persona-guide.md` 第 4 节初次建立。
6. **后续文件**：不预建；到达对应阶段时按 `file-templates.md` 创建。任何一步缺输入就停下提问，不跳到下一步。

## 信息充足性判断

不做整体“信息够了”的判断，按关卡逐项判断：

| 关卡 | 判断什么 | 不充足时 |
|---|---|---|
| 会话开始 | 是否指定模块 | 列清单，请用户选择 |
| 1.0 | 模块边界是否明确 | 记 S，引用或生成范围 Q，停止 |
| 1a | 本模块 brief 是否存在 | 不做 P 驱动的主动候选 |
| 1b | 27 个子提问是否各有显式引用 | 无引用即未覆盖，生成 Q |
| 1c | 四问和故事卡字段是否各有显式引用 | 无引用即缺口，生成 Q |
| 成形 | DoR 是否通过 | 留在候选 |
| 评审 | 五查 + 任一成员确认 | 退回或保持候选 |

每一关只认显式引用；没有引用就是缺口。模板只规定结构和可写内容，不预填答案；“待确认”是合法状态。

各文件的读取、写入、来源和写法见 `references/file-io.md`。

## 会话结束

如阶段、下一步或模块状态发生变化：

1. AI 提议更新 `STATUS.md`，列出改什么、为什么。
2. 任一成员确认。
3. AI 写入 `STATUS.md`；确认人和日期写在文件内；不写项目 D/CR。
4. 不改需求、不建 CR。

## 七步流程

1. **采集**：
   - **1.0 模块边界确认**：从 `00-vision.md`、`context.md`、`glossary.md`、`02-backlog.md` 确认模块边界。不明确时，记 S（用户选择的模块），先查 `07-dialogue.md` 是否已有范围 Q；有则引用原 Q，没有则生成一个范围 Q。无论哪种都停止；不做 brief、不做 27 项扫描、不生成功能问题。明确后进入 1a。如果 `00-vision.md` 尚未建立，先按 `references/vision-guide.md` 初次建立，再判断模块边界。
   - **1a 对标调研**（边界明确后）：按 `references/research-guide.md` 选 1～2 个平台，产出 brief；brief 是主动提问的依据，只提取用户可见行为，设计细节进 `docs/design-notes.md`
   - **1b 模块首访**：按 `references/coverage-scan.md` 的 27 个子提问逐项判断，产出 `docs/requirements/coverage-scan.md` 记录并更新 `coverage.md`；扫描只产出问题，不产出需求
   - **1c 缺口提问**：按 `references/gap-check.md` 对当前单位逐项检查；原话先记 S，只对“未覆盖 / 部分覆盖 / 无法判断 / 缺依据”生成 Q，进 `07-dialogue.md`；已有待答 Q 不重复。角色相关分析前，如果 `01-personas.md` 尚未建立，先按 `references/persona-guide.md` 初次建立
   - 文档缺失或为空时先报告，不凭记忆补全
2. **成形**：按 `references/extraction-guide.md` 提取；用故事卡（`references/story-card.md`），“原文摘录”必填；先过冲突检查（`references/conflict-check.md`）并记录结论；过 DoR；写 Given-When-Then；来源填 `S-/D-/R-`。
3. **排序**：MoSCoW 或价值-成本；给出建议，优先级由人决定并记录。
4. **建模**：只在文字说不清流程、状态、规则、交互或边界时画；查 `references/modeling-guide.md` 选最小图型。每个图元素必须有 `S/D/R/REQ` 来源；未回答的 Q、P、I 不作来源；设计进 `DSN-`。保存到 `models/<模块>-<主题>.mmd`，文件头写问题、来源、状态；另一人评审。
5. **评审**：另一人执行五查（`references/review-checklist.md`）：完整、一致、可测、可追踪、有据。
6. **验收标准确认**：标准可执行、无歧义后，需求可移交设计；到此为止。
7. **变更**：冲突检查 → 影响分析 → `06-changes.md` → 回填 `05-traceability.md`；冲突处理见 `references/conflict-check.md`。

## 成形四问

每条故事必须回答；问题进 Q，回答记为 S：
1. 角色：还有谁做这件事？
2. 触发：什么条件下发生？前置是什么？
3. 异常：失败、越权、边界时怎样？
4. 完成：怎么判断做成了？看到什么？留下什么记录？

四问只产生问题，不产生答案。

## 需求诊断输出

接到需求描述后，先分三栏，再动笔：
- **能确认的**：有 S/D/R 来源
- **需要问的**：编号 Q，指派确认人
- **不能写的**：无来源的推断、设计细节、范围外内容，写明原因

## 需求的两个来源

1. **用户描述**：用成形四问诊断缺口，问题引用用户原话（S）与缺口维度。
2. **AI 主动发现**：必须基于已登记来源（P/S/D/R），问题中写明依据；没有依据的只能作为开放问题，不得写成需求候选。

## 对话循环

1. 用户用自然语言描述需求，允许不符合故事卡格式。
1.5. AI 做写入前变更检查：新陈述与已确认条目不一致时，先展示两边原文并请用户选择，不直接写文件；细则见 `vision-guide.md` 第 6 节和 `file-io.md` 写入总则。
2. AI 按 `gap-check.md` 诊断缺口，输出“能确认的 / 需要问的 / 不能写的”。
3. AI 基于本模块 brief 主动补充遗漏，必须带 `P` 依据。
4. 用户回答 Q；把回答记为 S-xxx，并回填 `context.md` / `glossary.md`。
5. AI 把用户原话整理成故事卡：只重述、拆分、归一化用语，不新增内容。
6. 另一人评审，任一成员最终确认。
7. 进入下一个模块或下一组问题。

一次只处理一个模块或一组问题，不一次性生成整份需求文档。

## 冲突检查

新增、变更或转为“已确认”前执行：

1. 提取冲突画像：角色、对象、行为、条件、结果、权限、规则、生命周期、隐私、依赖、范围、术语
2. 在 backlog、NFR、愿景、术语表、上下文、追踪矩阵中检索重叠条目
3. 按十类冲突逐项比对
4. 结论：确定冲突 / 可能冲突 / 无冲突 / 无法判断
5. 记录检查维度、比对条目、依据、未覆盖项

详细清单与记录格式见 `references/conflict-check.md`。

## 状态流转

候选 → 已确认 → 开发中 → 已验收 → 已废弃
候选 → 已拒绝
已确认 / 开发中 → 变更中 → 已确认 / 开发中 / 已废弃

进入“已确认”：来源为 S/D/R + 五查通过 + backlog 的评审结果/日期 + 确认人/日期。
“已拒绝”由人决定并记 D；“变更中”表示已确认或开发中的需求正在变更，重新评审和确认后回到原状态或废弃。
AI 只能把需求写入“候选”；已确认、已拒绝、变更中由人决定并记录。

## DoR / DoD

**DoR**：故事卡字段齐全；有角色与价值、有来源、有可测验收标准、无未决依赖、一个迭代内可完成。
**DoD（需求侧）**：验收标准通过、五查通过、追踪矩阵已回填。
**模块门禁**：模块进入评审前，`coverage.md` 中该模块适用的六维不得为“未问”。

## 常见错误

| 错误 | 正确做法 |
|---|---|
| “首期按 Web/H5” | 端形态是范围决策，写 Q 等确认 |
| 自行规定 5 次锁定、视频 90% 完成 | 业务规则必须有来源，写 Q |
| 两句话扩出十几条需求 | 只写有来源的部分，其余进 Q |
| 用“合理补全”填空 | 红旗；改写成问题 |
| 需求里写心跳、死信队列、幂等 | 技术方案不属于需求，移交设计 |
| 把“比如登录”写成登录需求 | 先确认是举例还是真实需求 |
| 故事写“以便支撑后续分析”，但来源只说了记录 | 价值也必须有来源，否则写 Q |
| 竞品有这个功能，所以我们也要 | P 只生成 Q，竞品有 ≠ 我们要 |
| 需求里写知识追踪、缓存、微服务 | 设计细节进 `DSN-`，不进需求 |
