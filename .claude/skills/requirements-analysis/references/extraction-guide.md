# 提取规则

需求文件的内容不是 AI 原创，而是从规定来源提取，或由 AI 提议后经人确认。提取不是改写，更不是补全。

## 1. 合法来源

| 来源 | 能提取什么 | 不能做什么 |
|---|---|---|
| `S` | 用户原话、回答、确认 | 不改写、不补全 |
| `D` | 团队明确决定 | 不替人决定 |
| 已写入文件/用户提供的文档 | 文档明确写出的内容 | 不推论、不跨章节拼凑；在对话中引用文件名/章节 |
| `P` | 用户可见行为，仅用于提问 | 不直接写成需求 |
| `Q` | 问题 | 不作来源 |

推断不是来源，不进入“已确认”；需要保留时写 `Q` 或标为“AI 提议”。

## 2. 提取原则

- 故事和验收标准优先从 `S/D` 或已写入文件中提取；也可以由 AI 提议，标“AI 提议”，人确认后写入。
- 只重述、拆分、归一化；不新增未确认的角色、字段、规则、指标。
- 无法确认的内容写 Q，不写进故事。

### 诊断三栏（内部检查）

接到需求描述后，先按三栏检查：

- **能确认的**：有 `S/D` 来源；
- **需要问的**：编号 Q，写清依据；
- **不能直接写成已确认的**：无来源推断、设计细节、范围外内容；标“AI 提议”或 Q，写明原因。

三栏是内部检查，不在对话中逐栏展示。

### 需求的两个来源

1. **用户描述**：用成形四问诊断缺口，问题引用 `S` 与缺口维度；成形四问见 `elicitation-playbook.md`。
2. **AI 主动发现**：基于 `P/S/D` 的候选写明依据；AI 生成的候选标“AI 提议”；没有依据的作为开放问题或 Q，不写成已确认需求。

## 3. 从 S 提取

1. 先记 `S-xxx`，保留原句
2. 只做重述、拆分、归一化；不改范围、主体、条件、结果
3. 同义归一化只允许不改变含义的情况，例如“老师”→“教师”
4. 原文没有的角色、字段、规则、指标 → Q
5. “以便”价值必须有原文；没有则 Q，不写进故事

## 4. 从已写入文件或用户提供的文档提取

1. 引用到章节或条款，不能只写文档名
2. 只提取文档明确写出的内容
3. 不把“通常做法”或“推论”写成文档内容
4. 文档之间冲突：记录双方，生成 Q
5. 文档过时或只有部分内容：标证据强度

## 5. 从 P 提取（正式 brief）

正式 brief 中 `P` 只生成 Q；快速调研见 `research-guide.md`。`P` 可以支撑 AI 草案，但草案需人确认。

1. 判定“用户可见行为”：用户能看到、做到、得到什么；不是架构、算法、数据模型、技术栈
2. 每条观察带 `P-ID` 和证据强度
3. 观察写成“用户能……，以便……”或“用户看到……”
4. 设计细节 → `DSN-`
5. 把观察转成问题，例如：“P-xxx 中某平台教师能看周活动；我们是否需要？Q-xxx”
6. 用户回答后，答案记 `S`；需求来源写 `S`，不写 `P`

## 6. 从 D 提取

- 记录决策原文、依据
- 不把“会议讨论”写成 `D`；只有明确决定才是 `D`
- 决策变更：旧 `D` 标废弃，新建 `D`
- 冲突处理、基线变更必须有 `D`；优先级由人决定

## 7. 字段来源矩阵

| 字段 | 允许来源 | 没有来源时 |
|---|---|---|
| ID | 编号规则 | — |
| 标题 | `S/D`、已写入文件或 AI 提议经人确认 | Q |
| 故事 | `S/D`、已写入文件或 AI 提议经人确认 | Q |
| 验收标准 | `S/D`、已写入文件或 AI 提议经人确认 | Q |
| 优先级 | 人决定 | 待定 |
| 负责人 | 人指定 / `team.md` | 待指定 |
| 依赖 | 已有 `REQ` / 明确命名的外部系统 / 无 | Q；故事不写入 |

## 8. 提取步骤

1. 收集 `S/D`；已写入文件可直接引用
2. 起草故事和验收标准；AI 提议标“AI 提议”
3. 按字段矩阵逐项检查；缺的写 Q
4. 检查依赖：只写已有 `REQ` 或明确命名的外部系统；不确定写 Q
5. 检查是否新增角色、字段、规则、指标
6. 过冲突检查和 DoR
7. 人确认后写入

## 9. 确认对照

确认时逐句对照：

- 故事卡每个句子能否在 `S` 或已写入文件中找到依据？
- 有没有新增范围、条件、角色、字段、规则？
- “以便”价值是否来自依据？
- 验收标准的前置条件是否来自依据或回答？
- 依赖是否是已有 `REQ` 或明确命名的外部系统？
- 找不到依据 → Q，不写入。

## 10. 示例（通用示例，非本项目）

### 合格

`S-001`：“老师上传讲义后，学生应该能下载。下载失败要给出提示。”

故事：

> 作为学生，我希望下载教师上传的讲义。（价值未说明，见 Q-xxx；不写“以便”）

验收标准：

> Given 教师已上传讲义，When 学生下载讲义，Then 学生获得讲义；下载失败时给出提示。

### 不合格

- 加“以便复习/离线学习”：原文没有价值
- 加“重试按钮”：原文只说“给出提示”
- 加“登录后”：原文没有登录
- 加“视频也可下载”：原文只说讲义
- 把“老师”改成“任课教师”：改变了角色范围

## 11. 常见错误

- 把 `P` 观察直接写成需求
- 把未回答的 `Q` 当成答案
- 把“通常做法”当成依据

| 错误 | 正确做法 |
|---|---|
| “首期只做某一种端形态” | 端形态是范围决策，写 Q 等确认 |
| 自行规定重试次数、完成阈值 | 标为“AI 提议”或写 Q；人确认后才能写入 |
| 两句话扩出十几条需求 | 有依据的写成候选；其余标为“AI 提议”或 Q，写入前确认 |
| 用“合理补全”填空 | 标为“AI 提议”或 Q；写入前确认 |
| 需求里写重试队列、幂等、超时参数 | 技术方案不属于需求，移交设计 |
| 把“比如登录”写成登录需求 | 先确认是举例还是真实需求 |
| 故事写“以便支撑后续分析”，但来源只说了记录 | 价值需有依据或人的确认；否则写 Q |
| 竞品有这个功能，所以我们也要 | 竞品有 ≠ 我们要；P 可支撑 AI 提议，但最终需人确认 |
| 需求里写算法模型、缓存、微服务 | 设计细节进 `DSN-`，不进需求 |
- 故事写得顺，但找不到 `S` 或已写入文件的依据
- 把 AI 提议写成已确认内容
