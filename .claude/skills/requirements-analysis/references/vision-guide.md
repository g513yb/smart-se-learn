# 愿景与范围规则

## 1. 定位

`00-vision.md` 是项目的范围基线：说明为什么做、为谁、解决什么问题、本期做什么和不做什么、如何判断成功、有哪些项目级硬约束。它不记录具体需求、功能细节、验收标准、设计、计划、团队分工。

## 2. 六节结构与含义

| 章节 | 含义 | 应写 | 允许来源 | 不能写 |
|---|---|---|---|---|
| 项目定位 | 这个平台为谁、解决什么问题、是什么类型的平台 | 1～2 句，一段话 | `S/D/R` | 功能列表、技术栈 |
| 问题与目标 | 当前业务中最核心的问题，以及期望结果 | 问题陈述；结果用 bullet，每条一个 | `S/D/R` | 模块清单、功能列表、具体指标 |
| 范围 | 本期包含哪些主线/模块，明确不包含什么 | bullet；包含与不包含分开 | `S/D/R` | 具体需求、字段、流程 |
| 非目标 | 明确不做什么，防止范围蔓延 | bullet，每条一个判断 | `D/S/R` | “暂不考虑”这类模糊表述 |
| 成功标准 | 什么结果算成功，如何观察 | bullet：结果 + 指标/口径 | `D/S` | 无来源的数字、“体验良好” |
| 关键约束 | 项目级硬约束，如内容来源、合规、环境 | bullet | `S/D/R` | 详细 NFR、技术方案 |

## 3. 文件格式

```markdown
# 愿景与范围

填写规则见 `.claude/skills/requirements-analysis/references/vision-guide.md`。

| 基线版本 | 状态 | 确认人 | 确认日期 | 评审人 | 评审日期 | 最后变更 D | 最后变更 CR |
|---|---|---|---|---|---|---|---|
| v1 | 候选 / 待评审 / 已确认 / 退回 | 待填 | 待填 | 待填 | 待填 | D-xxx | — |

## 章节确认

| 章节 | 状态 | 确认人 | 确认日期 |
|---|---|---|---|
| 项目定位 | 待确认 | | |
| 问题与目标 | 待确认 | | |
| 范围 | 待确认 | | |
| 非目标 | 待确认 | | |
| 成功标准 | 待确认 | | |
| 关键约束 | 待确认 | | |

## 1. 项目定位

- ……（来源：S-xxx）

## 2. 问题与目标

- ……（来源：S-xxx）

## 3. 范围

- 包含：……（来源：S-xxx / R-xxx）
- 不包含：……（来源：S-xxx / D-xxx / R-xxx；未确认的不写正文，另记 Q 到 `07-dialogue.md`）

## 4. 非目标
```

每条内容都标来源；没有来源的条目不写，转 Q。文件内不写规则、流程、需求或设计。`Q` 不是来源；Q 被回答后，回答另记 `S`。

## 4. 初次建立

**适用判断**：文件没有基线版本表、没有 D、没有来源标注时，视为尚未正式建立；第一次按本节建立。已有版本表和 D 的文件，按第 5 节变更处理。

0. 旧格式正文逐条转为 S 或 Q，不得直接当作已确认内容；只有既有文档才能标 R。
1. AI 读现有 `00-vision.md`、`context.md`、`07-dialogue.md`、`08-decisions.md`
2. AI 按六节逐节问固定问题：
   - 项目定位：为谁？解决什么问题？是什么类型的平台？
   - 问题与目标：最核心的业务问题是什么？希望达到什么结果？
   - 范围：本期包含哪些主线/模块？明确不包含什么？
   - 非目标：哪些事明确不做？为什么？
   - 成功标准：什么结果算成功？用什么指标或口径观察？
   - 关键约束：有哪些项目级硬约束？
3. 用户回答记为 `S`，写入 `07-dialogue.md`
4. AI 只按 `S/D/R` 起草该节，标来源；不补内容
5. 任一成员逐节修改并确认；在“章节确认”表写状态、确认人、日期
6. AI 写入该节；缺来源的内容写 Q，不写正文
7. 六节确认后，另一人评审；评审通过后记 `D`“项目愿景基线建立”，写确认人和日期；基线版本表写 v1、状态“已确认”、确认人/日期、评审人/日期、最后变更 D、最后变更 CR 写“—”
8. 评审退回：状态“退回”，记录评审人/日期；修改受影响章节并重新确认后再评审；评审通过前不记 D
9. 初次建立没有变更前状态，不建 CR
10. AI 不能把任何一节标为“已确认”；确认、评审、日期由人填写

## 5. 后续变更

1. 用户提出变更或对话中出现隐含变更，记 `S`；AI 生成澄清 Q
2. 执行写入前变更检查（见第 6 节）
3. 影响与冲突检查
4. AI 起草变更前/后
5. 任一成员一人确认，记 `D`（确认人姓名、日期）
6. 写 `CR`：变更前/后、原因、影响、冲突检查、决策、评审人、确认人、状态“提议”
7. 另一人评审 CR：通过则状态“已批准”，写评审人/评审日期；不通过则“已拒绝”，`D` 标“已废弃”，不更新愿景文件
8. CR 批准后更新 `00-vision.md`：修改内容；受影响章节在“章节确认”表重置为“待确认”，逐节确认后更新状态/确认人/日期；基线版本递增；更新确认人/日期、评审人/日期、最后变更 D、最后变更 CR；CR 状态改“已执行”
9. 重跑受影响模块的 1.0
10. 更新追踪矩阵和受影响需求
11. CR 完成后状态改“已关闭”

初次建立不建 CR；已有基线后的任何内容变化都走本节。

## 6. 写入前变更检查

每次实质性陈述之后、写入任何文件之前执行。

1. 从 S 提取主体、属性、新值/新说法
2. 在已确认内容中查找同主体、同属性的条目
3. 结论只能是：新增 / 兼容补充 / 澄清 / 变更 / 冲突 / 无法判断
4. 对“变更 / 冲突 / 无法判断”，先展示两边原文：

> 你刚才说：“……。”（S-xxx）  
> 已确认的是：“……。”（D/REQ/R-xxx）  
> 请确认：修改已有条目 / 新增例外 / 只是澄清 / 不改。

5. 任一成员选择后，先判断基线是否已建立：
   - **修改已有条目**：基线已建立时走后续变更流程；初次建立时回到第 4 节，修改受影响章节并重新确认，不建 CR
   - **新增**：未确认时写 Q；确认后，若基线已建立，按变更流程记 D + CR；若仍在初次建立，按第 4 节写入
   - **新增例外**：基线已建立时记 D + CR，并在 CR 的“变更后/影响范围”写明例外；初次建立时按第 4 节写入正文，并在来源注释或 Q 中注明“例外”
   - **兼容补充**：先由任一成员确认是否改变含义；不改变时，基线已建立则按新增处理（D+CR），初次建立则第 4 节；改变时，基线已建立按变更，初次建立回到第 4 节重新确认；未确认写 Q
   - **澄清**：只改措辞且不改变含义，可直接更新；改变含义时，基线已建立按变更，初次建立回到第 4 节重新确认
   - **冲突**：按 `conflict-check.md` 展示双方，任一成员选择：修改 → 变更流程；新增例外 → 按新增例外；不改 → 基线已建立时记 D 维持现状，初次建立时写 Q 暂不写入；无法判断 → Q；选择前不写文件
   - **无法判断**：先追问一次；仍无法判断时写 Q，不写正文
   - **不改**：基线已建立时记 `D`“维持现有愿景条目不变”，写确认人和日期；不递增版本、不改章节、不建 CR；初次建立或旧格式无已确认条目时，写 Q“暂不写入”，不记 D
6. 没有成员选择时，不写文件。

AI 不能因为用户没说“修改”，就把新说法当成新需求或直接覆盖旧内容。

## 7. S/Q/D/CR 落点

- `S` / `Q`：`docs/requirements/07-dialogue.md`；格式见 `dialogue-log.md`
- `D`：`docs/requirements/08-decisions.md`；格式见 `decision-log.md`
- `CR`：`docs/requirements/06-changes.md`；表头见该文件，填写规则见 `file-io.md`
- 逐节确认：`00-vision.md` 的“章节确认”表
- AI 只能记录，不能替人填确认人、决策人、评审人、日期

## 8. 读取

- 会话开始：读全文。
- 1.0：用范围和目标判断模块是否在范围内。
- 1a/1b：用非目标过滤问题；属于非目标的能力不生成需求候选。
- 冲突检查：与 vision 冲突是范围冲突，比普通需求冲突更高一级。
- 基线变更：读变更前/后。
- 评审：五查“一致”包括与 vision 一致。

## 9. AI 边界

- 可以：按来源起草、指出缺口、生成 Q、比对范围冲突、逐节提问。
- 不可以：编目标、编非目标、编成功指标、把 `P` 当项目目标、把模块名当目标、替人决定范围、替人确认、替人填确认/评审记录。

## 10. 基线变更规则

- 项目基线初次建立记 `D`，不建 CR；已有基线后的变更记 `D` + CR。
- 变更由任一成员一人确认；另一人评审。
- 临时规则：当前文件存储无应用层，一人确认即可；应用层上线后重新评估是否恢复两人会签。
- 管理/流程规则变更记录在 `CLAUDE.md` 和 skill references，不写项目 D/CR。
