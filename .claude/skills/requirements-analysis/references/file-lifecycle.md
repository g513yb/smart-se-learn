# 文件生命周期与读写规则

本文件逐个定义需求文件的定位、结构、AI 填充步骤、建立时机、判定规则、确认方式，以及各阶段的读取、写入、来源和写法。结构模板见 `file-templates.md`；与 `SKILL.md` 冲突时，以 `SKILL.md` 硬规则为准。

## 一、通用规则

- AI 可以生成、起草、归纳、提议和写入内容。有 `S/D`、项目文件或人的回答作依据的内容优先使用；依据用来提高可信度和可追溯性，不是禁止 AI 生成的门槛。`P` 只生成 Q；`Q` 不是来源。
- AI 可以生成候选；候选必须标为“AI 提议”或“候选”，人确认后才能成为最终内容。
- AI 写入任何文件前，必须把最终内容交人确认；有依据不等于可以写入。人确认的内容记为 `S`。
- AI 在对话中输出内容时标明依据；文件内容不标来源。
- 已经写入文件且经人确认的内容可作为可靠依据；其来源记为 `S`。
- 事实候选提取和冲突检查是持续过程，不是单独阶段；提取不写入，写入必须人确认。
- 缺输入就停下提问，不推测没有依据的事实；无法判断时写 Q。
- AI 不自行决定 `D`、优先级、状态和范围归属；这些由人决定。AI 可以提议、记录或在人明确授权后写入。
- 不记录确认人、确认日期；确认在对话中完成。不记录评审人、评审结果、评审日期；评审规则已删除。
- 写文件前做变更检查；与已确认内容不一致时，先展示两边原文，由人选择。
- 每个文件只写本项目内容；流程、规则、确认方式不写进项目文件。
- 负责人从 `docs/team.md` 取；Q 不设确认人字段，记录回答人即可。
- 没有明确依据时，结论写“无法判断”或 Q，不写“通常”“应该”“行业常见”。
- 本节的通用规则优先于各文件节中的旧字段；各文件的评审/确认字段和来源标注在审查到该文件时删除。

### 读取

- 只读当前阶段需要的文件；不凭记忆补。
- 缺失或为空先报告；不把空文件当已知。
- 项目文件缺失且尚未初始化时，按 `SKILL.md` 的“初始化”顺序建立；只建结构，不预填内容。
- 读到的内容必须能说明依据：需求内容引用 `S/Q/D/R/P/REQ`；团队、状态等元数据引用人的回答 `S`；没有依据的不算已知。
- 已经写入文件且经人确认的内容可作为可靠依据；引用时按 `S` 处理。
- `P` 只帮助提问，不作答案。

### 写入

- AI 在对话中输出内容时标明依据；文件内容不标来源；AI 生成的内容必须标为候选或提议，并经人确认后写入。
- `Q` 是问题，不是来源；Q 的回答另记 `S`。
- 追加优先；覆盖前保留旧版本（git + 变更记录）。
- 模板字段不得留空；无内容写“无”或“待确认”。
- AI 不能替人做决定：`D`、优先级、状态由人决定；最终内容必须由人确认后写入；不记录确认人、确认日期。
- 设计内容只进 `design-notes.md` 的 `DSN-`，不进需求。
- 需求文档只写项目内容；流程、管理、确认规则不写入需求文档。发现规则文字，移到 skill reference，不在原处新增。
- 写前先做变更检查：新陈述与已确认条目不一致时，先展示两边原文并请人选择，不直接覆盖或新增。
- 不记录评审人、评审结果、评审日期；评审规则已删除。

## 四、各文件定义

### 1. `docs/team.md`

- **定位**：说明成员是谁、各自负责什么，为需求分配负责人提供姓名依据。不写需求、角色定义、权限矩阵。
- **建立**：初始化步骤 2。缺失时先建立，不能进入需要分配负责人的步骤。
- **读取**：会话开始、分配负责人前。
- **写入**：团队或分工变化时；人在对话中确认后，AI 写入。
- **结构**：成员、负责范围表。
- **各部分作用**：成员是可指派的姓名集合；负责范围是模块/层与人的映射。
- **AI 如何完成**：
  1. 问：成员有哪些？各自负责哪些范围？
  2. 人的回答记为 `S`，写入 `07-dialogue.md`。
  3. AI 从 `S` 中提取成员和范围；可基于回答和项目模块提出范围建议，标“建议”。
  4. 人确认后，AI 生成规范表格并写入。
- **判定规则**：
  - 负责人：模块落在唯一负责范围内 → 提议该负责人；无匹配或多匹配 → 问用户。
  - 负责范围：名称必须来自人的回答或项目文件；AI 可提议，但需人确认；没有依据写 Q。
- **禁止**：写需求、角色目标、权限矩阵；编造用户未提供的成员姓名；把建议写成已确认；未确认就写入。
- **确认**：人在对话中确认；不写项目 D/CR；不记录确认人/日期；无评审。

### 2. `docs/STATUS.md`

- **定位**：记录当前阶段、下一步和待决事项。不写需求内容。
- **建立**：初始化步骤 3；阶段、下一步或模块状态变化时更新。
- **读取**：会话开始、不确定进度时。
- **写入**：阶段、下一步或模块状态变化；AI 提议，人确认。
- **结构**：当前阶段、下一步、待决事项。
- **AI 如何完成**：
  1. 按下方“阶段判定表”从已有文件推导阶段。
  2. 只取最靠前的一个未完成关卡作为下一步。
  3. 列出待决事项：未回答的 Q、缺失输入、待人工决定的事项。
  4. 人确认后写入；不记录确认人/日期。
- **阶段判定表**：

| 已有文件与状态 | 当前阶段 |
|---|---|
| 无 team、STATUS、vision | 未初始化 |
| team、STATUS 已有，vision 缺失或无版本表/D | 愿景建立中 |
| vision 有 D，personas 缺失或无 D | 角色建立中 |
| vision、personas 有 D，尚未选模块 | 需求分析准备完成 |
| 已选模块，1.0 未通过 | 模块边界确认中 |
| 1.0 通过，1b/1c/成形未完成 | 模块需求分析中 |
| 本迭代目标需求已确认 | 需求确认完成 |

表外状态先问用户，不凭感觉写。
- **判定规则**：
  - 下一步只写一个关卡；多个事项写进待决事项。
  - 待决事项只写未解决项；已解决项删除。
  - 阶段变化才更新；无变化不写。
- **禁止**：写需求、假设、NFR；把建议写成已决定。
- **确认**：人在对话中确认；不写项目 D/CR；不记录确认人/日期；无评审。

### 3. `00-vision.md`

- **定位**：项目范围基线，回答为什么做、为谁、做什么/不做什么、如何判断成功、有哪些硬约束。不写需求、功能、验收标准、设计、计划。
- **建立**：初始化步骤 4；按 `vision-guide.md` 第 4 节初次建立；变更按第 5 节。
- **读取**：会话开始、1.0、冲突检查、基线变更。
- **写入**：初次建立或变更后；人确认后 AI 写入。
- **结构**：版本表、六节（项目定位、问题与目标、范围、非目标、成功标准、关键约束）。
- **各部分作用**：版本表记录基线版本；六节是范围基线内容。
- **AI 如何完成**：
  1. 按六节固定问题逐节问。
  2. 回答记 S，写入 `07-dialogue.md`。
  3. 起草时在对话中输出依据；可提出“AI 提议”；文件内容不标来源。
  4. 人逐节确认；未确认的章节不写入。
  5. 没有依据且人未确认的内容写 Q，不写正文。
- **判定规则**：
  - 目标 vs 范围：目标是期望结果；模块或功能清单是范围。出现模块清单时移到范围或 Q。
  - 关键约束 vs NFR：项目级硬约束进愿景；可度量指标进 NFR。
  - 非目标必须是否定判断；模糊的“暂不考虑”写 Q。
  - 成功标准必须有观察口径；没有依据的数字标为“AI 提议”或写 Q。
  - 范围明确 = 明确列出本期包含的模块/能力，且明确不包含什么；只有模块名不算明确。
- **禁止**：把 AI 提议写成已确认内容；把 P 当目标；把模块名当目标；未确认就写入。
- **确认**：人在对话中确认；初次记 D、不建 CR；变更记 D + CR；不记录确认/评审字段。

### 4. `01-personas.md`

- **定位**：定义平台有哪些角色、各自目标、场景、痛点和关系。不写功能、流程步骤、权限矩阵、界面、指标。
- **建立**：初始化步骤 5；按 `persona-guide.md` 第 4 节初次建立；变更按第 5 节。
- **读取**：1c 角色相关检查、冲突检查。
- **写入**：初次建立或变更后；人确认后 AI 写入。
- **结构**：基线版本、角色清单、角色卡（定义、目标、典型场景、痛点与约束、与其他角色的关系）。
- **各部分作用**：角色清单列出已确认角色；角色卡逐角色记录五节内容。
- **AI 如何完成**：
  1. 先问角色清单：平台有哪些角色？
  2. 每个角色按五节固定问题逐项问。
  3. 回答记 S；起草时在对话中输出依据；可提出“AI 提议”；文件内容不标来源。
  4. 人逐角色确认；未确认的角色不写入。
  5. 全部角色确认后写基线版本 v1。
- **判定规则**：
  - 角色 vs 外部系统：人会使用或被影响才是角色；系统或组织外部接口写 Q。
  - 角色 vs 权限：角色卡不写权限矩阵；权限进需求或横切问题。
  - 用户提到新角色但未确认：写 Q，不新增角色卡。
  - 场景四分：首次、日常、结束、异常；缺哪条写 Q。
- **禁止**：把 AI 提议写成已确认内容；写功能或解决方案；未确认就写入。
- **确认**：人在对话中确认；初次写 v1；变更递增版本；不记录评审/确认字段。

### 5. `context.md`

- **定位**：记录其他文件不收录的已确认稳定业务事实，供 1b/1c/冲突检查使用。不写需求、假设、设计。
- **建立**：第一次知识回填。
- **读取**：会话开始、1b、1c、冲突检查。
- **写入**：人确认稳定事实后；文件不标来源。
- **结构**：事实、说明。
- **AI 如何完成**：
  0. 持续提取：每次用户实质性陈述后扫描事实候选，不等待用户说“更新上下文”；候选标“AI 提议”，人确认后写入。
  1. 从 S 和已写入文件中找稳定事实；AI 可以提出事实候选，标“AI 提议”。
  2. 按下方判定判断是否稳定、是否应由本文件收录。
  3. 人确认后追加或更新；文件不标来源。
  4. 与已确认内容冲突时先展示两边原文，等人选择。
- **判定规则**：
  - 稳定事实 = 由 S 或已写入文件明确确认，不依赖某个具体功能实现，没有未决 Q，且其他文件未收录。
  - 描述“系统要做什么” → 不进 context，进 backlog 或 Q。
  - 描述“术语含义” → 进 glossary。
  - 描述“怎么实现” → 进 `design-notes.md`。
  - 愿景、角色、术语、需求或设计已收录的 → 不进 context。
  - 无法判断 → Q。
- **禁止**：把推断、P、未回答 Q、未确认的 AI 提议写成事实；写需求或设计。
- **确认**：人确认后写入；重大事实变更按冲突检查处理。

### 6. `glossary.md`

- **定位**：统一术语定义，保证需求、模型和讨论使用同一含义。不写需求、规则、设计。

- **写入**：人确认术语后；文件不标来源。
- **结构**：术语、定义。
- **AI 如何完成**：
  0. 持续提取：每次用户实质性陈述后扫描术语候选，不等待用户说“更新术语表”；候选标“AI 提议”，人确认后写入。
  1. 从 S 和已写入文件中找术语及其定义；AI 可以提出术语候选，标“AI 提议”。
  2. 做同义归一化，不改变含义。

- **禁止**：把未确认的 AI 提议写成定义；编造定义。
- **确认**：人确认后写入；术语变更按冲突检查处理。

### 7. `02-backlog.md`

- **定位**：需求故事卡池，记录故事、来源、验收标准、优先级、评审、确认、状态和未决问题。不写设计、算法、技术方案。
- **建立**：第一条故事卡；AI 只能写入“候选”。
- **读取**：会话开始、1b、1c、成形、冲突检查、评审、确认、变更。
- **写入**：追加或更新行；AI 只写候选和待评审字段。
- **结构**：表头见 `file-templates.md`，字段定义见 `story-card.md`。
- **各部分作用**：ID/标题/故事/原文摘录/来源保证可追溯；验收标准保证可测；优先级及依据由人决定；负责人/评审人来自分工；评审/确认记录人的结论；冲突检查记录筛查结果；依赖/未决问题标边界；状态表示生命周期。
- **AI 如何完成**：
  1. 从 S/D 提取；已写入文件可直接引用；原文摘录逐字复制。
  2. 只重述、拆分、归一化；不新增角色、字段、规则、指标。
  3. 写 Given-When-Then；写不出 Then → Q。
  4. 冲突检查并记录结论。
  5. 过 DoR；AI 写“候选”。
  6. 负责人/评审人按 `team.md` 提议；人确认。
  7. 优先级只给建议，人决定并记 D/S。
- **判定规则**：
  - 一条故事一个用户价值；多个价值拆分。
  - “以便”价值必须有来源；没有 → Q。
  - 验收标准的前置条件也必须可溯源；不能溯源 → Q。
  - 没有来源 → 可以写候选并标“AI 提议”，写入前需人确认；无法确认的写 Q。
  - 新增前检索 backlog 的同角色、同对象、同行为条目；重复 → 引用原 REQ 或问用户，不新建。
  - 需求跨模块 → 在主模块记录，关联模块写进依赖；归属不清 → 问用户，不自行拆分。
  - DoR 不通过 → 留候选，不进入确认。
  - 状态：AI 只能写候选；已确认、已拒绝、变更中、开发中、已验收、已废弃由人决定并记录。
- **DoR 可执行检查**：
  - 故事卡字段齐全。
  - 有来源（S/D）或人的确认；原文摘录非空；AI 提议可写“AI 生成，待确认”。
  - 验收标准至少一条主流程，异常流已列或写明待确认。
  - 依赖无未确认项；有未确认 Q 依赖 → 不通过。
  - 负责人确认可在一个迭代内完成；没有负责人或没有确认 → 不通过。
- **禁止**：把未确认的补充写成已确认内容；把 P 直接写成需求；把推断写成事实。
- **确认**：五查 + 评审人 ≠ 负责人 + 任一成员确认；升级状态需确认人/日期。

### 8. `03-nfr.md`

- **建立**：第一条 NFR；提问得到有来源的指标后。
- **读取**：1b、冲突检查、评审。

  - 已确认需求进入“变更中”；CR 批准后回到已确认或开发中；拒绝则保持原状态。
- **禁止**：AI 自行批准或执行 CR；删除旧版本。
- **确认**：任一成员确认 + 另一人评审；状态按词表。

### 12. `07-dialogue.md`

- **禁止**：把 Q 当来源；改写原话；编说话人、日期或回答。
- **确认**：S 状态“已记录”；Q 状态“待回答/已确认/已废弃”；AI 不替人确认。

- **禁止**：画未确认内容；把设计图画进需求模型。
- **确认**：另一人评审。

### 17. `design-notes.md`

- **定位**：记录设计线索（怎么做），供设计阶段参考。不进入需求。
- **建立**：第一条 DSN。
- **读取**：成形、冲突检查。
- **写入**：调研或讨论出现“怎么做”时。
- **结构**：编号、来源、观察到的做法、可能适用阶段、备注。
- **AI 如何完成**：
  1. 识别“怎么做”内容：架构、算法、数据模型、库、流程实现。
  2. 从需求讨论中移出，写 DSN。
  3. 标来源 P/S/D。
- **判定规则**：
  - “做什么/为什么” → 需求或 Q；“怎么做” → DSN。
  - P 观察中的实现方式 → DSN；用户可见行为 → Q。
  - 无法判断 → 问用户。
- **禁止**：把 DSN 写成需求；把需求写进设计线索。
- **确认**：设计阶段参考；不要求需求评审。

### 18. `research/<模块>.md`

- **定位**：记录 P 来源的用户可见行为观察，用于生成 Q。不是需求。
- **建立**：1.0 通过后的 1a。
- **读取**：1a、1b。
- **写入**：1a。
- **结构**：检索问题、来源清单、需求观察、设计线索、与本项目的差异、生成的 Q。
- **AI 如何完成**：
  1. 按 `research-guide.md` 选 1～2 个平台、3～5 个来源，只用已批准或部分验证来源。
  2. 只提取用户可见行为，标 P-ID 和证据强度。
  3. 设计细节进 `DSN-`；每条观察转 Q。
  4. 写差异和来源局限。
- **判定规则**：
  - 平台选择：同用户群、同能力、有官方文档或演示、成熟产品；选择理由写入 brief 的来源清单或差异节；不足 1 个已批准来源 → 停止，请用户提供材料。
  - 来源状态：候选需用户批准；排除来源不用。
  - 用户可见 = 用户能看到、做到、得到；架构、算法、数据模型不算。
  - 新增问题枯竭或达到时间盒 → 停止。
- **禁止**：把 P 写成需求、验收标准或优先级；整段复制。
- **确认**：brief 不是需求，不要求需求确认。

### 19. `research/sources/INDEX.md`、`research/platform-candidates.md`

- **定位**：登记 P 来源及验证状态。不写需求。
- **建立**：调研前或调研时。
- **读取**：1a。
- **写入**：来源验证或新增。
- **结构**：P-ID、标题、机构/作者、年份、URL 或文件、访问日期、类型、状态、证据强度。
- **AI 如何完成**：
  1. 登记来源。
  2. 验证可达性和官方性。
  3. 候选来源交用户批准。
  4. 排除来源保留编号，不进入 brief。
- **判定规则**：
  - 已批准和部分验证可用；候选需批准；缺失不可引用；排除不用。
  - 部分验证必须标注局限。
- **禁止**：把候选或排除来源写进 brief；伪造可达性。
- **确认**：用户批准候选来源。

### 20. 需求状态流转（跨文件）

- 候选 → 已确认 → 开发中 → 已验收 → 已废弃。
- 候选 → 已拒绝。
- 已确认或开发中 → 变更中 → 已确认、开发中或已废弃。
- AI 只能写“候选”；其他状态由人决定并记录。
- 进入“已确认”必须同时具备：来源 S/D、五查通过、backlog 评审结果/日期、确认人/日期。
- 进入“变更中”必须先有 CR。
- 状态变更缺少任一字段 → 不升级，写 Q 或停在原状态。

## 五、状态词表

- 需求 / 候选：候选 / 已确认 / 开发中 / 已验收 / 已废弃 / 已拒绝 / 变更中
- CR：提议 / 已批准 / 已执行 / 已拒绝 / 已关闭
- CR 类型：修正 / 行为变更 / 范围变更 / 废弃 / 冲突解决
- D：已决定 / 已废弃
- S：已记录 / 已废弃
- Q：待回答 / 已确认 / 已废弃

## 六、确认、决定

- 确认在对话中完成；AI 写入前必须得到人的明确确认；不记录确认人/确认日期。
- 评审规则已删除；不记录评审人、评审结果、评审日期。
- 决定写 `08-decisions.md` 的 D 表；决策人必须是姓名。
- 优先级依据写 `02-backlog.md` 的“优先级依据”，引用 D/S/Q。
- 变更决策写 `06-changes.md` 的“决策”，引用 D。

## 七、维护规则

- 新增文件、字段或状态时，先更新本文件和 `file-templates.md`，再改模板。
- 本文件与 `SKILL.md` 冲突时，以 `SKILL.md` 的硬规则为准，并修正本文件。
- 本文件不记录具体需求；只记录文件定义和读写规则。
