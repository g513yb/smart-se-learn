# 文件生命周期

本文件逐个定义需求文件的定位、结构、AI 填充步骤、建立时机、判定规则和确认方式。结构模板见 `file-templates.md`；阶段读写见 `file-io.md`。三处冲突时，以 `SKILL.md` 硬规则为准。

## 通用规则

- AI 可以生成、起草、归纳、提议和写入内容。有 `S/D/R`、项目文件或人的回答作依据的内容优先使用；依据用来提高可信度和可追溯性，不是禁止 AI 生成的门槛。`P` 只生成 Q；`Q` 不是来源。
- AI 可以生成候选；候选必须标为“AI 提议”或“候选”，人确认后才能成为最终内容。
- AI 写入任何文件前，必须把最终内容交人确认；有依据不等于可以写入。人确认的内容记为 `S`。
- 缺输入就停下提问，不推测没有依据的事实；无法判断时写 Q。
- AI 不自行决定 `D`、优先级、状态和范围归属；这些由人决定。AI 可以提议、记录或在人明确授权后写入。
- 不记录确认人、确认日期；确认在对话中完成。不记录评审人、评审结果、评审日期；评审规则已删除。
- 写文件前做变更检查；与已确认内容不一致时，先展示两边原文，由人选择。
- 每个文件只写本项目内容；流程、规则、确认方式不写进项目文件。
- 负责人从 `docs/team.md` 取；Q 不设确认人字段，记录回答人即可。
- 没有明确依据时，结论写“无法判断”或 Q，不写“通常”“应该”“行业常见”。
- 本节的通用规则优先于各文件节中的旧字段；各文件的评审/确认字段在审查到该文件时删除。

## 1. `docs/team.md`

- **定位**：说明成员是谁、各自负责什么，为需求分配负责人提供姓名依据。不写需求、角色定义、权限矩阵。
- **建立**：初始化步骤 2。缺失时先建立，不能进入需要分配负责人的步骤。
- **读取**：会话开始、分配负责人前。
- **写入**：团队或分工变化时；人在对话中确认后，AI 写入。
- **结构**：成员、负责范围表。
- **各部分作用**：成员是可指派的姓名集合；负责范围是模块/层与人的映射。
- **AI 如何完成**：
  1. 问：成员有哪些？各自负责哪些范围？
  2. 人的回答记为 `S`，写入 `07-dialogue.md`。
  3. AI 从 `S` 中提取成员和范围；可基于回答和项目模块提出范围建议，标“建议”。
  4. 人确认后，AI 生成规范表格并写入。
- **判定规则**：
  - 负责人：模块落在唯一负责范围内 → 提议该负责人；无匹配或多匹配 → 问用户。
  - 负责范围：名称必须来自人的回答或项目文件；AI 可提议，但需人确认；没有依据写 Q。
- **禁止**：写需求、角色目标、权限矩阵；编造用户未提供的成员姓名；把建议写成已确认；未确认就写入。
- **确认**：人在对话中确认；不写项目 D/CR；不记录确认人/日期；无评审。

## 2. `docs/STATUS.md`

- **定位**：记录当前阶段、下一步、迭代节奏和待决事项。不写需求内容。
- **建立**：初始化步骤 3；阶段、下一步或模块状态变化时更新。
- **读取**：会话开始、不确定进度时。
- **写入**：阶段、下一步或模块状态变化；AI 提议，人确认。
- **结构**：当前阶段、下一步、迭代节奏、待决事项。
- **AI 如何完成**：
  1. 按下方“阶段判定表”从已有文件推导阶段。
  2. 只取最靠前的一个未完成关卡作为下一步。
  3. 列出待决事项：未回答的 Q、缺失输入、待人工决定的事项。
  4. 人确认后写入；不记录确认人/日期。
- **阶段判定表**：

| 已有文件与状态 | 当前阶段 |
|---|---|
| 无 team、STATUS、vision | 未初始化 |
| team、STATUS 已有，vision 缺失或无版本表/D | 愿景建立中 |
| vision 有 D，personas 缺失或无 D | 角色建立中 |
| vision、personas 有 D，尚未选模块 | 需求分析准备完成 |
| 已选模块，1.0 未通过 | 模块边界确认中 |
| 1.0 通过，1b/1c/成形未完成 | 模块需求分析中 |
| 本迭代目标需求已确认 | 需求确认完成 |

表外状态先问用户，不凭感觉写。
- **判定规则**：
  - 下一步只写一个关卡；多个事项写进待决事项。
  - 待决事项只写未解决项；已解决项删除。
  - 阶段变化才更新；无变化不写。
- **禁止**：写需求、假设、NFR；把建议写成已决定。
- **确认**：人在对话中确认；不写项目 D/CR；不记录确认人/日期；无评审。

## 3. `00-vision.md`

- **定位**：项目范围基线，回答为什么做、为谁、做什么/不做什么、如何判断成功、有哪些硬约束。不写需求、功能、验收标准、设计、计划。
- **建立**：初始化步骤 4；按 `vision-guide.md` 第 4 节初次建立；变更按第 5 节。
- **读取**：会话开始、1.0、冲突检查、基线变更。
- **写入**：初次建立或变更后；AI 只起草。
- **结构**：版本表、章节确认表、六节（项目定位、问题与目标、范围、非目标、成功标准、关键约束）。
- **各部分作用**：版本表记录基线版本与确认/评审状态；章节确认表逐节记录确认；六节是范围基线内容。
- **AI 如何完成**：
  1. 按六节固定问题逐节问。
  2. 回答记 S，写入 `07-dialogue.md`。
  3. 只按 S/D/R 起草该节，标来源。
  4. 人逐节确认；另一人评审；评审通过记 D。
  5. 缺来源写 Q，不写正文。
- **判定规则**：
  - 目标 vs 范围：目标是期望结果；模块或功能清单是范围。出现模块清单时移到范围或 Q。
  - 关键约束 vs NFR：项目级硬约束进愿景；可度量指标进 NFR。
  - 非目标必须是否定判断；模糊的“暂不考虑”写 Q。
  - 成功标准必须有观察口径；没有来源的数字写 Q。
  - 范围明确 = 明确列出本期包含的模块/能力，且明确不包含什么；只有模块名不算明确。
- **禁止**：AI 填确认/评审/日期；把 P 当目标；把模块名当目标。
- **确认**：逐节确认 + 另一人评审 + D；初次不建 CR；变更记 D + CR。

## 4. `01-personas.md`

- **定位**：定义平台有哪些角色、各自目标、场景、痛点和关系。不写功能、流程步骤、权限矩阵、界面、指标。
- **建立**：初始化步骤 5；按 `persona-guide.md` 第 4 节初次建立；变更按第 5 节。
- **读取**：1c 角色相关检查、冲突检查、评审。
- **写入**：初次建立或变更后；AI 只起草。
- **结构**：基线元数据、角色清单、角色卡（定义、目标、典型场景、痛点与约束、与其他角色的关系）。
- **各部分作用**：角色清单说明谁在内、谁不在、谁待确认；角色卡逐角色记录五节内容。
- **AI 如何完成**：
  1. 先问角色清单：谁在内、谁不在、谁待确认。
  2. 每个角色按五节固定问题逐项问。
  3. 回答记 S；只按 S/D/R 起草，不补内容。
  4. 人逐角色确认；另一人评审；评审通过记 D。
- **判定规则**：
  - 角色 vs 外部系统：人会使用或被影响才是角色；系统或组织外部接口写 Q。
  - 角色 vs 权限：角色卡不写权限矩阵；权限进需求或横切问题。
  - 用户提到新角色但未确认：写 Q，不新增角色卡。
  - 场景四分：首次、日常、结束、异常；缺哪条写 Q。
- **禁止**：编角色、目标、场景、痛点、关系；写功能或解决方案。
- **确认**：逐角色确认 + 另一人评审 + D；初次不建 CR。

## 5. `context.md`

- **定位**：记录已确认的稳定业务事实（背景、角色职责、对象、规则），供 1b/1c/冲突检查使用。不写需求、假设、设计。
- **建立**：第一次知识回填。
- **读取**：会话开始、1b、1c、冲突检查。
- **写入**：Q 被回答且回答稳定后；每条标来源。
- **结构**：业务背景、角色与职责、关键业务对象、业务规则与政策、术语指针。
- **AI 如何完成**：
  1. 从 S 中找稳定事实。
  2. 按下方判定判断是否稳定。
  3. 追加或更新对应小节；每条标 S 编号。
  4. 与已确认内容冲突时先展示两边原文，等人选择。
- **判定规则**：
  - 稳定事实 = 由 S/D/R 明确确认，不依赖某个具体功能实现，且没有未决 Q。
  - 描述“系统要做什么” → 不进 context，进 backlog 或 Q。
  - 描述“术语含义” → 进 glossary。
  - 描述“怎么实现” → 进 `design-notes.md`。
  - 无法判断 → Q。
- **禁止**：把推断、P、未回答 Q 写成事实；写需求或设计。
- **确认**：来源为 S；重大事实变更按冲突检查处理。

## 6. `glossary.md`

- **定位**：统一术语定义，保证需求、模型和讨论使用同一含义。不写需求、规则、设计。
- **建立**：第一次知识回填；术语被确认时。
- **读取**：会话开始、1b、1c、命名或接口设计前。
- **写入**：术语被确认后；标来源。
- **结构**：术语、定义、来源。
- **AI 如何完成**：
  1. 从 S 中找术语及其定义。
  2. 做同义归一化，不改变含义。
  3. 写入表格；来源写 S。
  4. 定义不清或有多义 → Q。
- **判定规则**：
  - 算术语 = 在需求、规则或模型中反复使用，且含义影响理解；一次性的普通词不建条目。
  - 同义词统一到一个术语，其他标“别名”。
  - 模块缩写由用户在 1.0 确认，记入本表；AI 不自行缩写。
- **禁止**：编定义；把未确认的解释写成定义。
- **确认**：来源为 S；术语变更按冲突检查处理。

## 7. `02-backlog.md`

- **定位**：需求故事卡池，记录故事、来源、验收标准、优先级、评审、确认、状态和未决问题。不写设计、算法、技术方案。
- **建立**：第一条故事卡；AI 只能写入“候选”。
- **读取**：会话开始、1b、1c、成形、冲突检查、评审、确认、变更。
- **写入**：追加或更新行；AI 只写候选和待评审字段。
- **结构**：表头见 `file-templates.md`，字段定义见 `story-card.md`。
- **各部分作用**：ID/标题/故事/原文摘录/来源保证可追溯；验收标准保证可测；优先级及依据由人决定；负责人/评审人来自分工；评审/确认记录人的结论；冲突检查记录筛查结果；依赖/未决问题标边界；状态表示生命周期。
- **AI 如何完成**：
  1. 从 S/D/R 提取；原文摘录逐字复制。
  2. 只重述、拆分、归一化；不新增角色、字段、规则、指标。
  3. 写 Given-When-Then；写不出 Then → Q。
  4. 冲突检查并记录结论。
  5. 过 DoR；AI 写“候选”。
  6. 负责人/评审人按 `team.md` 提议；人确认。
  7. 优先级只给建议，人决定并记 D/S。
- **判定规则**：
  - 一条故事一个用户价值；多个价值拆分。
  - “以便”价值必须有来源；没有 → Q。
  - 验收标准的前置条件也必须可溯源；不能溯源 → Q。
  - 没有来源 → 可以写候选并标“AI 提议”，写入前需人确认；无法确认的写 Q。
  - 新增前检索 backlog 的同角色、同对象、同行为条目；重复 → 引用原 REQ 或问用户，不新建。
  - 需求跨模块 → 在主模块记录，关联模块写进依赖；归属不清 → 问用户，不自行拆分。
  - DoR 不通过 → 留候选，不进入确认。
  - 状态：AI 只能写候选；已确认、已拒绝、变更中、开发中、已验收、已废弃由人决定并记录。
- **DoR 可执行检查**：
  - 故事卡字段齐全。
  - 有来源（S/D/R）或人的确认；原文摘录非空；AI 提议可写“AI 生成，待确认”。
  - 验收标准至少一条主流程，异常流已列或写明待确认。
  - 依赖无未确认项；有未确认 Q 依赖 → 不通过。
  - 负责人确认可在一个迭代内完成；没有负责人或没有确认 → 不通过。
- **禁止**：把未确认的补充写成已确认内容；把 P 直接写成需求；把推断写成事实。
- **确认**：五查 + 评审人 ≠ 负责人 + 任一成员确认；升级状态需确认人/日期。

## 8. `03-nfr.md`

- **定位**：记录非功能需求（性能、可用性、安全、隐私、可解释性、兼容性、可维护性、合规）。不写功能需求。
- **建立**：第一条 NFR；提问得到有来源的指标后。
- **读取**：1b、冲突检查、评审。
- **写入**：NFR 确认后。
- **结构**：类别、指标、场景与边界、来源、状态、评审人、评审日期、确认人、确认日期。
- **AI 如何完成**：
  1. 按 `nfr-checklist.md` 逐项问。
  2. 有来源、场景和边界 → 起草；缺一 → Q。
  3. 另一人评审；任一成员确认后写确认字段。
- **判定规则**：
  - 指标必须可测：数值、单位、场景、边界齐全；否则 Q。
  - 没有来源的数字 → Q，不写“行业常见”。
  - 安全、隐私、性能目标必须另一人评审。
  - 涉及合规或项目基线时，任一成员确认 + 另一人评审。
- **禁止**：编阈值；把设计目标写成需求；把 P 当来源。
- **确认**：评审 + 确认；变更走 CR。

## 9. `04-hypotheses.md`

- **定位**：记录无法直接写成确定需求的探索型问题，用假设卡验证。不承诺功能。
- **建立**：第一张假设卡；满足下方触发条件时。
- **读取**：1b、成形。
- **写入**：假设卡评审后。
- **结构**：ID、假设、来源、验证指标、验证方式、失败判据、决策、关联需求、状态、确认人、确认日期。
- **AI 如何完成**：
  1. 判断是否需要假设卡。
  2. 按 `hypothesis-card.md` 问全字段。
  3. 缺指标、验证方式或失败判据 → Q，不写卡。
  4. 另一人评审验证设计；任一成员确认。
- **判定规则**：
  - 用户提出“要做什么”且有来源 → 需求，不是假设。
  - 用户提出“这样做会不会改善 X”或“AI 能不能做到”，结果不确定 → 假设卡。
  - 无法判断 → Q。
  - 假设卡不替代需求；需要交付的行为仍写需求。
- **禁止**：把假设写成功能承诺；事后补失败判据。
- **确认**：评审 + 确认；结果回写并记 D。

## 10. `05-traceability.md`

- **定位**：记录需求到验收标准、模型、设计、代码、测试、变更和交接的追踪关系。不写需求内容。
- **建立**：第一次确认或交接。
- **读取**：冲突检查、变更、评审、交接。
- **写入**：确认、设计、提交、测试、交接或基线变更后。
- **结构**：需求 ID、验收标准、模型、设计、代码提交、测试、变更记录、交接、状态。
- **AI 如何完成**：
  1. 只填人能提供或工件中明确写出 REQ ID 的链接。
  2. 没有链接写“待确认”。
  3. 状态用 `file-io.md` 的状态词表。
- **判定规则**：
  - 代码提交或测试只有在提交信息、测试名或工件明确含 REQ ID 时才能关联；否则问人，不猜。
  - 设计文档必须明确引用 REQ ID；否则不填。
  - 变更记录必须引用 CR ID。
  - 模型必须引用 REQ ID 或 S/D/R 来源。
- **禁止**：凭文件名、目录或提交时间推测关联；把“相关”写成“已覆盖”。
- **确认**：人的确认或交接记录。

## 11. `06-changes.md`

- **定位**：记录已确认需求或项目基线的变更。不写新需求。
- **建立**：第一个 CR。
- **读取**：变更、冲突检查。
- **写入**：变更或冲突决策后。
- **结构**：CR-ID、日期、类型、目标需求、变更前、变更后、原因/依据、影响范围、冲突检查、决策、评审人、评审日期、确认人、确认日期、状态。
- **AI 如何完成**：
  1. 判断是变更还是澄清。
  2. 影响分析：按 `conflict-check.md` 的画像检索 backlog、NFR、愿景、术语表、上下文和追踪矩阵；逐条记“受影响/不受影响”及依据；未覆盖项写 Q。
  3. 起草变更前/后。
  4. 任一成员确认并记 D；写 CR，状态“提议”。
  5. 另一人评审；批准后执行；更新目标文件和追踪矩阵。
- **影响范围**：必须列出受影响的 REQ、文档或模块；没有影响也要写“已检查，未发现”，并列出检查维度。
- **判定规则**：
  - 改变行为、范围、权限、数据、规则或验收标准 → CR。
  - 只改措辞且含义不变 → 澄清，可直接更新，不建 CR。
  - 无法判断 → Q，不写文件。
  - 已确认需求进入“变更中”；CR 批准后回到已确认或开发中；拒绝则保持原状态。
- **禁止**：AI 自行批准或执行 CR；删除旧版本。
- **确认**：任一成员确认 + 另一人评审；状态按词表。

## 12. `07-dialogue.md`

- **定位**：记录用户原话 S 和缺口问题 Q，是需求的原始证据。不写需求。
- **建立**：第一次记录 S。
- **读取**：会话开始、1.0、愿景/角色初次建立、1b、1c、成形、基线变更。
- **写入**：每次 S/Q；Q 回答后另记 S 并回填。
- **结构**：S 表（编号、原话、说话人、日期、状态、关联）和 Q 表（编号、问题、依据、状态、回答、回答人、日期、关联）。
- **各部分作用**：S 是来源和边界；Q 是缺口与待答；回答人记录谁回答了问题。
- **AI 如何完成**：
  1. 用户说话先记 S，逐字保存，不改写。
  2. 从 S 和检查项生成 Q；每个 Q 带依据和具体缺口。
  3. Q 记录回答人；无法判断时问用户。
  4. Q 回答后另记 S，Q 状态改“已确认”，回答列写“见 S-xxx”。
- **判定规则**：
  - 用户陈述、回答、确认 → S；AI 的问题 → Q；AI 的推断 → 不进 S/Q，写 Q 或 I。
  - 一句话含多个问题 → 拆成多个 Q。
  - 已有 Q 覆盖 → 引用原 Q，不重复。
  - 说话人、日期必须有人提供；AI 不编。
- **禁止**：把 Q 当来源；改写原话；编说话人、日期或回答。
- **确认**：S 状态“已记录”；Q 状态“待回答/已确认/已废弃”；AI 不替人确认。

## 13. `08-decisions.md`

- **定位**：记录人的明确决策 D。不写讨论、建议或 AI 判断。
- **建立**：第一次记录 D。
- **读取**：冲突检查、排序、愿景/角色初次建立、基线变更。
- **写入**：人做决定时。
- **结构**：D-ID、日期、决策、依据、决策人、影响需求/文档、状态。
- **AI 如何完成**：
  1. 确认这是明确决定，不是讨论或倾向。
  2. 记录决策原文、依据、决策人姓名和日期。
  3. 写清影响的需求或文档。
- **判定规则**：
  - 明确决定 → D；讨论、建议、倾向 → 不写。
  - 决策人必须是姓名；AI 不编。
  - 新决定取代旧决定 → 旧 D 标“已废弃”，新建 D。
- **禁止**：AI 替人决定；编决策人或日期；把 AI 建议写成 D。
- **确认**：决策人即确认人；状态“已决定/已废弃”。

## 14. `coverage.md`

- **定位**：记录模块六维覆盖状态。不写需求。
- **建立**：1b 首次扫描。
- **读取**：会话开始、1b、模块评审前。
- **写入**：1b 扫描后。
- **结构**：模块、角色、旅程、对象、规则、横切、质量、对标调研。
- **AI 如何完成**：
  1. 模块清单来自 `00-vision.md` 的范围；愿景缺失先建立。
  2. 按 `coverage-scan.md` 第 7 节计算每维状态。
  3. 只写状态，不写需求。
- **判定规则**：
  - 任一子提问未覆盖 → 该维“未问”；建 Q 后“已问待答”。
  - 全部适用项由确认需求覆盖 → “有需求”。
  - 全部适用项已覆盖（需求或已确认知识） → “已确认”。
  - 任一无法判断 → “无法判断”。
  - 全部不适用 → “不适用”。
  - “对标调研”列“已调研”只表示有 brief，不表示覆盖。
- **禁止**：用 P 证明覆盖；把“未问”写成“已问待答”。
- **确认**：扫描人记录；模块评审前检查。

## 15. `coverage-scan.md`

- **定位**：记录 27 项扫描的逐项证据和缺口。不写需求。
- **建立**：1b 首次扫描。
- **读取**：1b。
- **写入**：扫描后。
- **结构**：模块头、输入清单、扫描记录、维度聚合、清单外建议、输出。
- **AI 如何完成**：
  1. 前置检查：1.0 通过、边界明确、输入可用；不通过则停止。
  2. 逐项查显式引用：S、REQ、R、NFR、context、glossary、Q；P 只帮助提问。
  3. 分类；无引用即未覆盖；生成 Q。
  4. 聚合到 `coverage.md`。
- **判定规则**：
  - 每个非“未覆盖”结论必须有显式编号；没有就是未覆盖。
  - 部分覆盖或未覆盖 → 生成 Q；已问待答 → 不重复。
  - 不适用必须有明确排除声明；AI 自判不算。
  - 27 项是闭集；清单外建议需用户批准。
- **禁止**：写需求或故事卡；把 P 当覆盖依据；用“行业常见”补。
- **确认**：扫描人；模块评审前检查。

## 16. `models/`

- **定位**：用图回答文字说不清的问题。不写设计或架构。
- **建立**：第一次建模；满足 `modeling-guide.md` 的触发条件时。
- **读取**：建模时。
- **写入**：按需。
- **结构**：`models/<模块>-<主题>.mmd`，一图一文件，文件头写问题、来源、状态。
- **AI 如何完成**：
  1. 先写图要回答的问题。
  2. 按 `modeling-guide.md` 选最小图型。
  3. 每个元素标 S/D/R/REQ；没有来源不画。
  4. 未回答 Q、P、I 不作来源；设计进 `DSN-`。
  5. 保存；另一人评审。
- **判定规则**：
  - 一句话、无分支、无状态、无多角色 → 不画。
  - 流程 3 步以上或 2 个以上分支 → 活动图。
  - 3 个以上状态或迁移 → 状态图。
  - 3 个以上条件组合 → 决策表。
  - 3 个以上角色/外部系统交互 → 时序图。
  - 角色能力范围不清 → 用例图。
  - 3 个以上核心概念关系不清 → 领域类图。
  - 主题 = 图回答的问题的短名；不明确时问用户。
- **禁止**：画未确认内容；把设计图画进需求模型。
- **确认**：另一人评审。

## 17. `design-notes.md`

- **定位**：记录设计线索（怎么做），供设计阶段参考。不进入需求。
- **建立**：第一条 DSN。
- **读取**：成形、冲突检查。
- **写入**：调研或讨论出现“怎么做”时。
- **结构**：编号、来源、观察到的做法、可能适用阶段、备注。
- **AI 如何完成**：
  1. 识别“怎么做”内容：架构、算法、数据模型、库、流程实现。
  2. 从需求讨论中移出，写 DSN。
  3. 标来源 P/S/D。
- **判定规则**：
  - “做什么/为什么” → 需求或 Q；“怎么做” → DSN。
  - P 观察中的实现方式 → DSN；用户可见行为 → Q。
  - 无法判断 → 问用户。
- **禁止**：把 DSN 写成需求；把需求写进设计线索。
- **确认**：设计阶段参考；不要求需求评审。

## 18. `research/<模块>.md`

- **定位**：记录 P 来源的用户可见行为观察，用于生成 Q。不是需求。
- **建立**：1.0 通过后的 1a。
- **读取**：1a、1b。
- **写入**：1a。
- **结构**：检索问题、来源清单、需求观察、设计线索、与本项目的差异、生成的 Q。
- **AI 如何完成**：
  1. 按 `research-guide.md` 选 1～2 个平台、3～5 个来源，只用已批准或部分验证来源。
  2. 只提取用户可见行为，标 P-ID 和证据强度。
  3. 设计细节进 `DSN-`；每条观察转 Q。
  4. 写差异和来源局限。

## 20. 需求状态流转（跨文件）

- 候选 → 已确认 → 开发中 → 已验收 → 已废弃。
- 候选 → 已拒绝。
- 已确认或开发中 → 变更中 → 已确认、开发中或已废弃。
- AI 只能写“候选”；其他状态由人决定并记录。
- 进入“已确认”必须同时具备：来源 S/D/R、五查通过、backlog 评审结果/日期、确认人/日期。
- 进入“变更中”必须先有 CR。
- 状态变更缺少任一字段 → 不升级，写 Q 或停在原状态。
