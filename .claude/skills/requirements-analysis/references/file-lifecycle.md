# 文件生命周期与读写规则

本文件逐个定义需求文件的定位、结构、AI 填充步骤、建立时机、判定规则、确认方式，以及各阶段的读取、写入、来源和写法。结构模板见 `file-templates.md`；与 `SKILL.md` 冲突时，以 `SKILL.md` 硬规则为准。

## 一、通用规则

- AI 可以生成、起草、归纳、提议和写入内容。有 `S/D`、项目文件或人的回答作依据的内容优先使用；依据用来提高可信度和可追溯性，不是禁止 AI 生成的门槛。`P` 可以生成 Q，也可以支撑 AI 草案；`P` 不是最终来源；`Q` 不是来源。
- AI 可以生成候选；候选必须标为“AI 提议”或“候选”，人确认后才能成为最终内容。
- 需求内容、backlog、基线（`vision.md`、`personas.md`）写入前，必须把最终内容交人确认；有依据不等于可以写入。记录层（S/Q/D 的记录、Q 回答回写、`docs/STATUS.md` 维护）由 AI 自动完成，不需要逐条确认，不在对话中说明。用户自己的产品或需求陈述记为 `S`；角色输入写入 `personas.md`，团队输入写入 `docs/team.md`，状态由 AI 维护，均不记 `S`；简短确认和仅依赖问题的答复记入 Q 的回答列；AI 草案经人确认、修改或纠正后直接写入目标文件，不记为 `S`。
- 对话层按 `conversation-style.md` 说明依据；文件内容不标来源。
- 已经写入文件且经人确认的内容可作为可靠依据；不追溯为 `S`。
- 事实候选提取和冲突检查是持续过程，不是单独阶段；提取不写入，写入必须人确认。
- 缺输入就停下提问，不推测没有依据的事实；无法判断时写 Q。
- AI 不自行决定 `D`、优先级、状态和范围归属；这些由人决定。AI 可以提议、记录或在人明确授权后写入。
- 不记录确认人、确认日期；确认在对话中完成。不记录评审人、评审结果、评审日期；评审规则已删除。
- 写文件前做变更检查；与已确认内容不一致时，先展示两边原文，由人选择。
- 每个文件只写本项目内容；流程、规则、确认方式不写进项目文件。
- 负责人从 `docs/team.md` 取；Q 不设确认人、回答人字段；用户用自己的话回答记入 Q 的回答列，回答本身补充了新内容时才另记 `S`；角色回答写入 `personas.md`，团队信息写入 `docs/team.md`，均不记 `S`；简短确认不记 `S`；采用、修改或纠正 AI 草案不记 `S`，直接写入目标文件。
- 没有明确依据时，结论写“无法判断”或 Q，不写“通常”“应该”“行业常见”。
- 本节的通用规则优先于各文件节中的旧字段；各文件的评审/确认字段和来源标注在审查到该文件时删除。

### 读取

- 只读当前阶段需要的文件；不凭记忆补。
- 缺失或为空先报告；不把空文件当已知。
- 项目文件缺失且尚未初始化时，按 `SKILL.md` 的“初始化”顺序建立；只建结构，不预填内容。
- 读到的内容必须能说明依据：需求内容引用 `S/Q/D/R/P/REQ` 或已写入文件；团队元数据引用 `docs/team.md`；状态引用 `STATUS.md`；没有依据的不算已知。
- 已经写入文件且经人确认的内容可作为可靠依据；引用时按已确认文件处理，不记为 `S`。
- `P` 可帮助提问或支撑 AI 草案，但不能作最终答案或最终来源。

### 写入

- 对话层按 `conversation-style.md` 说明依据；文件内容不标来源；AI 生成的需求内容、backlog 条目和基线内容必须标为候选或提议，并经人确认后写入；记录层按本节的记录规则自动完成。`STATUS.md` 是推导出的运行状态，不视为候选内容，按阶段判定表自行维护。
- `Q` 是问题，不是来源；Q 的回答写入回答列，补充新内容时才另记 `S`；简短确认不记 `S`。
- 追加优先；覆盖前保留旧版本（git + 变更记录）。
- 模板字段不得留空；无内容写“无”或“待确认”。
- AI 不能替人做决定：`D`、优先级、需求内容由人决定；最终需求内容必须由人确认后写入。`STATUS.md` 例外：AI 按阶段判定表自行维护。不记录确认人、确认日期。
- 设计内容只进 `design-notes.md` 的 `DSN-`，不进需求。
- 需求文档只写项目内容；流程、管理、确认规则不写入需求文档。发现规则文字，移到 skill reference，不在原处新增。
- 写前先做变更检查：新陈述与已确认条目不一致时，先展示两边原文并请人选择，不直接覆盖或新增。
- 不记录评审人、评审结果、评审日期；评审规则已删除。

## 四、各文件定义

### 1. `docs/team.md`

- **定位**：说明成员是谁、各自负责什么，为需求分配负责人提供角色依据。不写需求、角色定义、权限矩阵。
- **建立**：初始化步骤 3。愿景范围确认后建立；缺失时不能进入需要分配负责人的步骤。
- **读取**：会话开始、分配负责人前。
- **写入**：团队或分工变化时；人在对话中确认后，AI 写入。
- **结构**：成员、角色/简称/负责范围表。
- **各部分作用**：成员是可指派的角色集合；简称用于需求负责人字段；负责范围是模块/层与角色的映射，模块/能力名称来自已确认的 `vision.md` 范围节，按职能层划分时写清对应关系。
- **AI 如何完成**：
  1. 愿景范围确认后问：成员有哪些？各自负责哪些范围？
  2. 团队信息（角色、简称、负责范围）写入 `docs/team.md`，不记 `S`；需要澄清的写 Q。
  3. AI 从回答和已确认的愿景范围中提取成员、角色简称和范围；可提出范围建议，标“建议”。
  4. 人确认后，AI 生成规范表格并写入。
- **判定规则**：
  - 负责人：模块落在唯一负责范围内 → 提议该负责人；无匹配或多匹配 → 问用户。
  - 负责范围：名称必须来自人的回答或已确认的项目文件（通常为 `vision.md` 范围节）；AI 可提议，但需人确认；没有依据写 Q。
- **禁止**：写需求、角色目标、权限矩阵；编造用户未提供的成员角色；把建议写成已确认；未确认就写入。
- **确认**：人在对话中确认；不写项目 D；不记录确认人/日期；无评审。

### 2. `docs/STATUS.md`

- **定位**：记录当前阶段、当前模块、下一步和待决事项。不写需求内容。
- **建立**：初始化步骤 4；阶段、下一步、模块状态或待决事项变化时更新。
- **读取**：会话开始、不确定进度时。
- **写入**：阶段、下一步、模块状态或待决事项变化时，AI 按阶段判定表自行更新；不需要人确认，不在对话中说明。
- **结构**：当前阶段、当前模块、下一步、待决事项。
- **AI 如何完成**：
  1. 按下方“阶段判定表”从已有文件推导阶段。
  2. 只取最靠前的一个未完成关卡作为下一步。
  3. 列出待决事项：`dialogue.md` 中状态为“待回答”或“部分回答”的全部 Q；缺失输入；待人工决定的事项。
  4. AI 直接写入；不记录确认人/日期；不在对话中说明。
- **阶段判定表**：

| 已有文件与状态 | 当前阶段 |
|---|---|
| 无 vision、team、STATUS | 未初始化 |
| vision 缺失或无版本表/D（其余情况） | 愿景建立中 |
| vision 有 D，team 或 STATUS 缺失 | 团队与状态建立中 |
| vision 有 D、team 和 STATUS 已有，personas 缺失或版本表不是 v1 | 角色建立中 |
| vision 有 D、personas 有版本表 v1，尚未选模块 | 需求分析准备完成 |
| 已选模块，边界确认未通过 | 模块边界确认中 |
| 边界确认通过，模块首访/缺口提问/成形未完成 | 模块需求分析中 |
| 存在待回答/部分回答的 Q，或 S/Q 关联列仍为“待建” | 待决事项处理中 |
| 本迭代目标需求已确认，且无待回答/部分回答的 Q、无“待建”关联列 | 需求确认完成 |
| 用户确认移交包 | 已移交设计 |

阻塞项 = 使当前阶段无法通过的未满足条件。当前阶段为“待决事项处理中”时，阻塞项是仍未回答的 Q 和仍为“待建”的 S/Q 关联列。移交阻断项见 `handoff.md` 第 2.1 节。

表外状态：AI 写“无法判断”，不凭感觉猜；只有该状态影响下一步时，才在具体步骤中提问。
- **判定规则**：
  - 下一步只写一个关卡；多个事项写进待决事项。
  - 待决事项只写未解决项；已解决项删除。
  - 阶段、下一步、模块状态或待决事项变化时更新；无变化不写。
- **禁止**：写需求、假设、NFR；把建议写成已决定。
- **确认**：不需要人确认；AI 按阶段判定表自行维护；不写项目 D；不记录确认人/日期；无评审。

### 3. `vision.md`

- **定位**：项目范围基线，回答为什么做、为谁、做什么/不做什么、如何判断成功、有哪些硬约束。不写需求、功能、验收标准、设计、计划。
- **建立**：初始化步骤 2；按 `vision-guide.md` 第 4 节初次建立；变更按第 5 节。
- **读取**：会话开始、边界确认、冲突检查、基线变更。
- **写入**：初次建立或变更后；人确认后 AI 写入。
- **结构**：版本表、六节（项目定位、问题与目标、范围、非目标、成功标准、关键约束）。
- **各部分作用**：版本表记录基线版本；六节是范围基线内容。
- **AI 如何完成**：
  1. 按六节固定问题逐节、逐问。
  2. 回答记 S，写入 `dialogue.md`。
  3. 起草时按 `conversation-style.md` 说明依据；可提出“AI 提议”；文件内容不标来源。
  4. 人逐节确认；未确认的章节不写入。
  5. 没有依据且人未确认的内容写 Q，不写正文。
- **判定规则**：
  - 目标 vs 范围：目标是期望结果；模块或功能清单是范围。出现模块清单时移到范围或 Q。
  - 关键约束 vs NFR：项目级硬约束进愿景；可度量指标进 NFR。
  - 非目标必须是否定判断；模糊的“暂不考虑”写 Q。
  - 成功标准必须有观察口径；没有依据的数字标为“AI 提议”或写 Q。
  - 范围明确 = 明确列出本期包含的模块/能力，且明确不包含什么；只有模块名不算明确。
- **禁止**：把 AI 提议写成已确认内容；把 P 当目标；把模块名当目标；未确认就写入。
- **确认**：人在对话中确认；初次记 D；变更记 D；不记录确认/评审字段。

### 4. `personas.md`

- **定位**：定义平台有哪些角色、各自目标、场景、痛点和关系。不写功能、流程步骤、权限矩阵、界面、指标。
- **建立**：初始化步骤 5；按 `persona-guide.md` 第 4 节初次建立；变更按第 5 节。
- **读取**：缺口提问中的角色相关检查、冲突检查。
- **写入**：初次建立或变更后；人确认后 AI 写入。
- **结构**：基线版本、角色清单、角色卡（定义、目标、典型场景、痛点与约束、与其他角色的关系）。
- **各部分作用**：角色清单列出已确认角色；角色卡逐角色记录五节内容。
- **AI 如何完成**：
  1. 先问角色清单：平台有哪些角色？
  2. 每个角色按五节固定问题逐项问。
  3. 回答用于起草角色卡，不记 S；起草时按 `conversation-style.md` 说明依据；可提出“AI 提议”；文件内容不标来源。
  4. 人逐角色确认；未确认的角色不写入。
  5. 全部角色确认后写基线版本 v1。
- **判定规则**：
  - 角色 vs 外部系统：人会使用或被影响才是角色；系统或组织外部接口写 Q。
  - 角色 vs 权限：角色卡不写权限矩阵；权限进需求或横切问题。
  - 用户提到新角色但未确认：写 Q，不新增角色卡。
  - 场景四分：首次、日常、结束、异常；缺哪条写 Q。
- **禁止**：把 AI 提议写成已确认内容；写功能或解决方案；未确认就写入。
- **确认**：人在对话中确认；初次写 v1；变更递增版本；不记录评审/确认字段。

### 5. `context.md`

- **定位**：记录其他文件不收录的已确认稳定业务事实，供模块首访/缺口提问/冲突检查使用。不写需求、假设、设计。
- **建立**：第一次知识回填；没有跨文件稳定事实时不建，缺失正常。
- **读取**：会话开始、模块首访、缺口提问、冲突检查。
- **写入**：人确认稳定事实后；文件不标来源。
- **结构**：事实、说明。
- **AI 如何完成**：
  0. 持续提取：每次用户实质性陈述后扫描事实候选，不等待用户说“更新上下文”；候选标“AI 提议”，人确认后写入。
  1. 从 S 和已写入文件中找稳定事实；AI 可以提出事实候选，标“AI 提议”。
  2. 按下方判定判断是否稳定、是否应由本文件收录。
  3. 人确认后追加或更新；文件不标来源。
  4. 与已确认内容冲突时先展示两边原文，等人选择。
- **判定规则**：
  - 稳定事实 = 由 S 或已写入文件明确确认，不依赖某个具体功能实现，没有未决 Q，且其他文件未收录。
  - 描述“系统要做什么” → 不进 context，进 backlog 或 Q。
  - 描述“术语含义” → 进 glossary。
  - 描述“怎么实现” → 进 `design-notes.md`。
  - 愿景、角色、术语、需求或设计已收录的 → 不进 context。
  - 无法判断 → Q。
- **禁止**：把推断、P、未回答 Q、未确认的 AI 提议写成事实；写需求或设计。
- **确认**：人确认后写入；重大事实变更按冲突检查处理。

### 6. `glossary.md`

- **定位**：统一术语定义，保证需求、模型和讨论使用同一含义。不写需求、规则、设计。
- **建立**：第一次知识回填；术语被确认时。
- **读取**：会话开始、模块首访、缺口提问、命名或接口设计前。
- **写入**：人确认术语后；文件不标来源。
- **结构**：术语、定义。
- **AI 如何完成**：
  0. 持续提取：每次用户实质性陈述后扫描术语候选，不等待用户说“更新术语表”；候选标“AI 提议”，人确认后写入。
  1. 从 S 和已写入文件中找术语及其定义；AI 可以提出术语候选，标“AI 提议”。
  2. 做同义归一化，不改变含义。
  3. 人确认后写入；文件不标来源。
  4. 定义不清或有多义 → Q。
- **判定规则**：
  - 算术语 = 在需求、规则或模型中反复使用，且含义影响理解；一次性的普通词不建条目。
  - 同义词统一到一个术语，其他标“别名”。
  - 模块缩写由用户在边界确认时指定，记入本表；AI 不自行缩写。
- **禁止**：把未确认的 AI 提议写成定义；编造定义。
- **确认**：人确认后写入；术语变更按冲突检查处理。

### 7. `backlog.md`

- **定位**：需求故事卡池，记录已确认的故事、验收标准、优先级、负责人和依赖。不写设计、算法、技术方案。
- **建立**：第一条故事卡。
- **读取**：会话开始、模块首访、缺口提问、成形、冲突检查、变更。
- **写入**：人确认后追加或更新行。
- **结构**：表头见 `file-templates.md`，字段定义见 `story-card.md`。
- **各部分作用**：ID/标题/故事/验收标准是需求内容；优先级由人决定；负责人来自分工；依赖表示验收或使用的前置条件。
- **AI 如何完成**：
  0. 持续提取：每次用户实质性陈述后扫描需求候选；候选标“AI 提议”，人确认后写入。
  1. 从 S、已写入文件或 AI 提议中生成故事；只重述、拆分、归一化。
  2. 识别依赖：只基于故事/验收标准中的显式前置条件或已有 REQ，提出 `REQ-xxx` / 外部系统 / 无；不确定 → Q。
  3. 写 Given-When-Then；写不出 Then → Q。
  4. 冲突检查；检索 backlog 同角色、同对象、同行为条目，避免重复。
  5. 过 DoR；人确认后写入。
  6. 写入后检索同模块、同角色的 Q，把对应 Q 的关联需求改为本 `REQ-xxx`；S 的关联列补上 Q。
  7. 负责人按 `team.md` 提议；无匹配问人。
  8. 优先级只给建议，人决定。
- **判定规则**：
  - 一条故事一个用户价值；多个价值拆分。
  - 故事和验收标准只写已确认内容；未确认细节写 Q。
  - 验收标准必须可观察；前置条件必须可确认。
  - 依赖只写 `REQ-xxx`（已写入 backlog）、明确命名的外部系统、`无`。
  - 不写实现依赖、传递依赖、未写入 backlog 的需求、模糊表述。
  - 有未确认依赖 → Q，故事不写入。
  - 重复 → 引用原 REQ 或问用户，不新建。
  - 需求跨模块 → 在主模块记录，关联模块写进故事或 Q；归属不清 → 问用户。
  - DoR 不通过 → 不写入。
- **DoR 可执行检查**：
  - ID、标题、故事、验收标准、优先级、负责人、依赖齐全。
  - 故事和验收标准已经人确认。
  - 验收标准至少一条主流程，异常流已写或写明 Q。
  - 依赖已存在或已确认；没有未确认依赖。
  - 关联 Q 全部已确认或已废弃，且相关 Q 的关联需求已回填 `REQ-xxx`；存在“待回答/部分回答”或“待建” → 不写入。
  - 负责人确认可在一个迭代内完成。
- **DoD（需求侧）**：验收标准经人确认。
- **依赖的使用规则**：
  1. 读取 backlog 时，读取每条故事的依赖；只解析直接依赖，不展开传递依赖。
  2. 写入前校验：
     - `REQ-xxx` 必须已在 backlog 中存在；
     - 外部系统必须由人明确命名并确认；
     - 禁止自依赖；
     - 检测循环依赖，发现循环 → Q，故事不写入；
     - 无法校验 → Q，故事不写入。
  3. AI 可以基于直接依赖提出排序或影响分析建议，但必须说明依据；排序由人决定。
  4. 依赖被删除或改名时，AI 检索 backlog 中引用该 `REQ-xxx` 的故事，列出并请人决定是否更新。
  5. 外部系统名称不清楚时，先问用户；必要时记入 `glossary.md`，不自行命名。
  6. 不推断实现依赖、传递依赖，不把代码/接口/架构写进依赖。
- **禁止**：把未确认的补充写成已确认内容；把 P 直接写成需求；把推断写成事实；写设计；推断实现依赖或传递依赖。
- **确认**：人在对话中确认后写入；不记录评审/确认/状态/D 字段。

### 8. `nfr.md`

- **定位**：记录非功能需求（性能、可用性、安全、隐私、可解释性、兼容性、可维护性、合规）。不写功能需求。
- **建立**：第一条 NFR；模块边界明确后，模块首访的质量维度或用户提出质量要求时即可开始；不等待 backlog 完成。
- **读取**：模块首访、冲突检查。
- **写入**：人确认后写入。
- **结构**：ID、类别、指标、场景与边界。
- **各部分作用**：ID 是 `NFR-<三位序号>` 引用编号；类别对应 `nfr-checklist.md` 的八类；指标是可测的质量目标；场景与边界是指标成立的条件。
- **AI 如何完成**：
  1. 按 `nfr-checklist.md` 逐项问。
  2. 指标和场景与边界齐全 → 起草；可提出“AI 提议”；缺一 → Q。
  3. 人确认后写入；文件不标来源。
- **判定规则**：
  - NFR 与 backlog 并行；写 NFR 前检查相关 backlog 故事，避免脱节。
  - 指标必须可测：指标名、数值、单位、测量口径齐全，或可验证的规则；否则 Q。
  - 场景与边界必须写清适用的操作/数据量/并发/环境/时间窗口/角色；整行必须可验收。
  - 没有依据的数字：标“AI 提议”，人确认后写入；无法确认写 Q。
  - 不写“行业常见”。
- **禁止**：编阈值；把设计目标写成需求；把 P 当依据；未确认就写入。
- **确认**：人确认后写入；变更按对话确认后更新；不记录评审/确认/状态/D 字段。

### 9. `dialogue.md`

- **定位**：记录产品或需求陈述 S 和缺口问题 Q，是需求的原始证据。角色输入写入 `personas.md`；团队输入写入 `docs/team.md`。不写需求。
- **建立**：第一次记录 S。
- **读取**：会话开始、边界确认、愿景初次建立、模块首访、缺口提问、成形、基线变更。
- **写入**：每次产品或需求陈述 S/Q；角色、团队、状态输入不写入本文件；Q 回答写入回答列并回填；仅在回答补充新内容时另记 S。
- **结构**：S 表（编号、原话、状态、关联需求/问题）和 Q 表（编号、问题、依据、状态、回答、关联需求）。
- **各部分作用**：S 是来源和边界；Q 是缺口与待答；关联需求/问题把 S、Q 和需求连起来。
- **AI 如何完成**：
  1. 用户说话：只收产品或需求陈述；角色、团队、状态输入写入各自文件；人的提问不进 S。
  2. 记 S 原话，逐字保存，不改写。
  3. 从 S 和检查项提取需求、术语、事实；对遗漏部分逐一提问。
  4. 用户用自己的话回答 → 写入 Q 的回答列；回答本身补充了新内容时才另记 S；简短确认不记 S；采用、修改或纠正 AI 草案 → 不记 S，直接写入目标文件；全部答完并由人确认后，Q 状态改“已确认”；部分回答标“部分回答”；回答列可写回答原文、多个 S 或“已采用 AI 草案，见目标文件”。
  5. 人不回答 → AI 按规则提出草案和依据；人确认后写入对应文件；未确认不写入。
  6. 同一 REQ 可以由多条 S/Q 支持；需求写入 backlog 前，检查关联 Q 是否全部“已确认/已废弃”。
- **判定规则**：
  - 用户自己的产品或需求独立陈述 → S；角色、团队、状态输入 → 不记 S，写入各自文件；人的提问 → 不进 S；简短确认、仅依赖问题的答复 → 写入 Q 的回答列，不记 S；AI 草案的采用/确认/纠正 → 不进 S；AI 的问题 → Q；AI 的推断 → 不进 S/Q，写 Q 或标为“AI 提议”。
  - 拆分 S 时，每个 S 必须能独立成立；依赖前句的片段合并。
  - 一句话含多个问题 → 拆成多个 Q。
  - 已有 Q 覆盖 → 引用原 Q，不重复。
  - AI 不编原话、不编回答。
- **S 矛盾处理**：
  - 发现 S 前后矛盾时，暂停提取、提问和写入，先处理矛盾。
  - 同一主体、同一属性、不同结论 → 矛盾候选；展示双方，人选择。
  - 修改 S 前做影响分析：按 `dialogue-log.md` 的影响分析清单逐文件检查（vision、personas、context、glossary、backlog、NFR、models、design-notes、decisions、coverage-scan、dialogue、research），每个文件给出受影响/不受影响/无相关条目/无法判断；无法判断写 Q；只有人确认的条目才更新。
  - 只有人确认的条目才更新；AI 不自行判定谁取代谁。
  - 详细规则见 `dialogue-log.md`“S 矛盾处理”。
- **禁止**：把 Q 当来源；改写原话；编原话或回答。
- **确认**：S 状态“已记录/已废弃”；Q 状态“待回答/部分回答/已确认/已废弃”；AI 不替人确认。

### 10. `decisions.md`

- **定位**：记录人的明确决策 D。不写讨论、建议或 AI 判断。
- **建立**：第一次记录 D。
- **读取**：冲突检查、愿景初次建立、其他明确决策。
- **写入**：人做决定时。
- **结构**：D-ID、决策、依据、影响需求/文档、状态。
- **AI 如何完成**：
  1. 确认这是明确决定，不是讨论或倾向。
  2. 记录决策原文、依据。
  3. 写清影响的需求或文档。
- **判定规则**：
  - 明确决定 → D；讨论、建议、倾向 → 不写。
  - 内容确认（采用 AI 草案、接受 AI 提取的最终版本）→ 不写 D。
  - 新决定取代旧决定 → 旧 D 标“已废弃”，新建 D。
- **禁止**：AI 替人决定；把 AI 建议写成 D。
- **确认**：状态“已决定/已废弃”。

### 11. `coverage-scan.md`

- **定位**：记录 27 项扫描的逐项证据和缺口。不写需求。
- **建立**：模块首访首次扫描。
- **读取**：会话开始（只读模块覆盖总览）、模块首访、模块确认前。
- **写入**：扫描后。
- **结构**：模块覆盖总览、模块头、输入清单、扫描记录、维度聚合、清单外建议、输出。
- **AI 如何完成**：
  1. 前置检查：边界确认通过、边界明确、输入可用；不通过则停止。
  2. 逐项查显式引用：S、REQ、NFR、D、context、glossary、已写入文件、Q；P 只帮助提问。
  3. 分类；无引用即未覆盖；生成 Q。
  4. 聚合到本文件的模块覆盖总览。
- **判定规则**：
  - 每个非“未覆盖”结论必须有显式编号；没有就是未覆盖。
  - 部分覆盖或未覆盖 → 生成 Q；已问待答 → 不重复。
  - 不适用必须有明确排除声明；AI 自判不算。
  - 27 项是闭集；清单外建议需用户批准。
- **禁止**：写需求或故事卡；把 P 当覆盖依据；用“行业常见”补。
- **确认**：扫描人记录；模块确认前检查。

### 12. `models/`

- **定位**：用图回答文字说不清的问题。不写设计或架构。
- **建立**：第一次建模；满足 `modeling-guide.md` 的触发条件时。
- **读取**：建模时。
- **写入**：按需。
- **结构**：源在 `models/src/`（Mermaid 为 `<模块>-<主题>.mmd`，表格为 `.md`），导出图在 `models/img/`，目录表为 `models/README.md`；一图一源一图，同一图只保留一种图像格式；文件头写问题、来源。
- **AI 如何完成**：
  1. 先写图要回答的问题。
  2. 按 `modeling-guide.md` 选最小图型。
  3. 每个元素标 S/D/REQ；没有来源不画。
  4. 未回答 Q、P、推断不作来源；设计进 `DSN-`。
  5. 人确认后保存。
- **判定规则**：
  - 一句话、无分支、无状态、无多角色 → 不画。
  - 流程 3 步以上或 2 个以上分支 → 活动图。
  - 3 个以上状态或迁移 → 状态图。
  - 3 个以上条件组合 → 决策表。
  - 3 个以上角色/外部系统交互 → 时序图。
  - 角色能力范围不清 → 用例图。
  - 3 个以上核心概念关系不清 → 领域类图。
  - 主题 = 图回答的问题的短名；不明确时问用户。
- **禁止**：画未确认内容；把设计图画进需求模型。
- **确认**：人确认。

### 13. `design-notes.md`

- **定位**：记录设计线索（怎么做），供设计阶段参考。不进入需求。
- **建立**：第一条 DSN。
- **读取**：成形、冲突检查。
- **写入**：调研或讨论出现“怎么做”时。
- **结构**：编号、来源、观察到的做法、可能适用阶段、备注。
- **AI 如何完成**：
  1. 识别“怎么做”内容：架构、算法、数据模型、库、流程实现。
  2. 从需求讨论中移出，写 DSN。
  3. 标来源 P/S/D。
- **判定规则**：
  - “做什么/为什么” → 需求或 Q；“怎么做” → DSN。
  - P 观察中的实现方式 → DSN；用户可见行为 → Q。
  - 无法判断 → 问用户。
- **禁止**：把 DSN 写成需求；把需求写进设计线索。
- **确认**：设计阶段参考；不记录评审/确认/状态/D/CR。

### 14. `research/<模块>.md`

- **定位**：记录 P 来源的用户可见行为观察，用于生成 Q。不是需求。
- **建立**：边界确认通过后的对标调研。
- **读取**：对标调研、模块首访。
- **写入**：对标调研。
- **结构**：检索问题、来源清单、需求观察、设计线索、与本项目的差异、生成的 Q。
- **AI 如何完成**：
  1. 按 `research-guide.md` 选 1～2 个平台、3～5 个来源，只用已批准或部分验证来源。
  2. 只提取用户可见行为，标 P-ID 和证据强度。
  3. 设计细节进 `DSN-`；每条观察转 Q。
  4. 写差异和来源局限。
- **快速调研**：AI 准备提出遗漏内容但不确定时，可查 1～2 个已批准来源，输出 P 观察 + Q + 可选 AI 草案；草案标“AI 提议”，人确认后写入；不写正式 brief。
- **判定规则**：
  - 平台选择：同用户群、同能力、有官方文档或演示、成熟产品；选择理由写入 brief 的来源清单或差异节；不足 1 个已批准来源 → 停止，请用户提供材料。
  - 来源状态：候选需用户批准；排除来源不用。
  - 用户可见 = 用户能看到、做到、得到；架构、算法、数据模型不算。
  - 快速调研只作线索，不作事实性结论；需要系统分析时回到正式对标调研 brief。
  - 新增问题枯竭或达到时间盒 → 停止。
- **禁止**：把 P 写成需求、验收标准或优先级；整段复制。
- **确认**：brief 不是需求；不记录评审/确认/状态/D/CR。

### 15. `research/sources/INDEX.md`

- **定位**：登记 P 来源及验证状态。不写需求。
- **建立**：调研前或调研时。
- **读取**：对标调研。
- **写入**：来源验证或新增。
- **结构**：P-ID、标题、机构/作者、年份、类型、模块、状态、证据强度、备注；文件/URL 见文件清单，访问日期见文件头。
- **AI 如何完成**：
  1. 登记来源。
  2. 验证可达性和官方性。
  3. 候选来源交用户批准。
  4. 排除来源保留编号，不进入 brief。
- **判定规则**：
  - 已批准和部分验证可用；候选需批准；缺失不可引用；排除不用。
  - 部分验证必须标注局限。
- **禁止**：把候选或排除来源写进 brief；伪造可达性。
- **确认**：用户批准候选来源。

### 16. 写入与更新（跨文件）

- AI 只写人确认后的需求内容；`STATUS.md` 例外：AI 按阶段判定表自行维护。更新故事前先确认。
- 需求文件不设状态字段，不记录评审/确认/D；`D` 的状态见第五部分状态词表。
- 变更通过对话确认后直接更新目标文件；影响其他文件时按冲突检查处理。

## 五、状态词表

- D：已决定 / 已废弃
- S：已记录 / 已废弃
- Q：待回答 / 部分回答 / 已确认 / 已废弃

## 六、确认、决定

- 确认在对话中完成；AI 写入前必须得到人的明确确认；不记录确认人/确认日期。
- 评审规则已删除；不记录评审人、评审结果、评审日期。
- 决定写 `decisions.md` 的 D 表；AI 只记录。
- 优先级依据写 `backlog.md` 的“优先级依据”，引用 D/S/Q。

## 七、维护规则

- 新增文件、字段或状态时，先更新本文件和 `file-templates.md`，再改模板。
- 本文件与 `SKILL.md` 冲突时，以 `SKILL.md` 的硬规则为准，并修正本文件。
- 本文件不记录具体需求；只记录文件定义和读写规则。

## 八、初始化顺序

适用：会话开始时项目文件缺失，或用户要求从零建立。初始化只建立结构、愿景与角色基线、团队信息和项目状态，不写需求、假设、NFR 或验收标准。

1. **检查**：按 `file-templates.md` 的文件清单逐项检查，列出存在与缺失；不把缺失当已知，不预建空文件。
2. **愿景**：按 `vision-guide.md` 第 4 节初次建立。回答先记 `S`；第一次需要 `S` 时按 `file-templates.md` 创建 `dialogue.md`，第一次需要 `D` 时创建 `decisions.md`。愿景的范围节是团队分工和模块选择的依据；范围不明确时停下补 Q。
3. **团队与分工**：愿景范围确认后，问清成员、角色简称和各自负责范围。范围名称应能对应愿景范围中的模块/能力；AI 从回答和已确认的愿景范围中提取并起草 `docs/team.md`，不记 `S`；可提出范围建议；人确认后写入。不写项目 D；不记录确认人/日期。
4. **项目状态**：AI 按本文件的 STATUS 阶段判定表，从已有文件推导当前阶段、下一步和待决事项，按 `file-templates.md` 创建或更新 `docs/STATUS.md`；不需要人确认，不在对话中说明；不写项目 D；不记录确认人/日期。
5. **角色**：按 `persona-guide.md` 第 4 节初次建立。
6. **后续文件**：不预建；到达对应阶段时按 `file-templates.md` 创建。任何一步缺输入就停下提问，不跳到下一步。
