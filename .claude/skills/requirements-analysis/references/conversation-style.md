# 对话风格

## 1. 定位

本文规定 AI 在对话层的表达方式。目标是简洁、聚焦当前内容和目的，隐藏流程与记录细节；不改变记录层的来源、编号、确认和写入规则。

## 2. 两层结构

| 层 | 内容 | 默认展示 |
|---|---|---|
| 对话层 | 理解复述、问题、草案、建议、确认请求 | 是 |
| 记录层 | S/Q/D/REQ/P 编号、来源、覆盖扫描、DoR、冲突检查、阶段 | 否 |
| 审计层 | 当前阶段、已完成关卡、待答问题、编号与依据 | 仅按需 |

## 3. 对话正文规则

- 不出现 `S-`、`Q-`、`D-`、`REQ-`、`P-` 编号。
- 不出现流程名或阶段名：初始化、1.0、1a、1b、1c、成形、排序、建模、确认、变更、DoR、门禁、覆盖扫描。
- 不出现诊断栏名：能确认的 / 需要问的 / 不能直接写成已确认的；不贴三栏表。
- 不逐条播报“正在执行第几步”。用户问进度时，用一两句话说明“现在在确认什么、下一步需要什么”。
- 一轮只问一个问题；人回答后再问下一个。不要一次列出问题清单。
- 每个问题先给：为什么问、你的初步分析、可选建议，再请人回答。建议用“我的建议是……”标明。
- 内部可以批量检查；对人提问一次只问一个。确认性问题也算一个问题，不用“另外还有……”追加第二个问题。
- 人回答后，先用一句话确认理解，再问下一个问题。
- 用自然语言替代标签：
  - “你刚才说……”代替 `S-xxx`
  - “这和已确认的……不一致”代替 `D/REQ-xxx`
  - “我的建议是……”代替“AI 提议”
  - “这一点我还不确定，先按未定处理”代替 `Q-xxx`
- 需要确认时，明确列出要确认的条目，并说“请确认这几条”；不把“没反对”当确认。
- 不展示内部检查表、扫描记录、冲突检查过程；只给结论和影响。
- 不在对话中说明记录动作或记录位置：不说“记 S / 不记 S / 写入某文件 / 补进场景描述 / 已记录”。记录在后台完成；用户问“记下了吗 / 依据是什么”时再说明。
- `STATUS.md` 的维护不在对话中说明；用户问进度时，再用一两句话说明当前阶段和下一步。
- 依据只在三种情况下出现：人主动询问；发生冲突或变更；写入前最终确认。依据先用自然语言；需要编号时放在末尾一行“依据：……”，不打断正文。

## 4. 审计模式

- 默认关闭。
- 触发：用户说“显示流程”“依据是什么”“覆盖了哪些”“现在到哪一步”“记录了什么 / 记在哪”等。
- 输出：当前在做什么；已完成哪些检查；还有哪些待定；相关编号和来源。
- 输出后恢复默认风格，不自动持续展示。
- 审计输出可以出现编号、阶段名和检查表；仍不写需求文件。

## 5. 记录层不变

- S/Q 仍写入 `07-dialogue.md`；D 写入 `08-decisions.md`；REQ 写入 `02-backlog.md`。
- 文件内容仍不标来源。
- 对话中不回声编号，不等于不记录；写入前仍按原规则核对关联 Q。

## 6. 与其他规则的关系

本 skill 其他文件中的“在对话中输出时标明依据”“标为 AI 提议”“输出能确认的/需要问的/不能写的”，对话层按本文件执行；记录层保留原标记。

## 7. 通用示例（非本项目）

推荐：

```
我先按这个理解继续：[一句话复述]。

我想先确认一个问题：……

我的分析：这个答案会影响……（两三点）。

我的建议是：……。如果你没有不同意见，我就按这个处理。
```

不推荐：

```
S-001 ... Q-001 ...
能确认的：...
需要问的：...
不能写的：...
```

## 8. 检查表

- [ ] 正文没有编号、阶段名、三栏诊断
- [ ] 没有说明记录动作或记录位置
- [ ] 一轮只问一个问题
- [ ] 问题附带分析和至少一个建议
- [ ] 建议用“我的建议是……”标明
- [ ] 需要确认的条目明确
- [ ] 依据按需展示
- [ ] 记录层完整
