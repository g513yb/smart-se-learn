# 对话记录

S = 用户陈述（原话、回答、确认），是需求来源。
Q = 缺口问题，不是来源；回答记为 S。

本文中的编号和内容均为通用示例，不对应本项目。

|---|---|---|---|---|---|

## 缺口问题（Q）

|---|---|---|---|---|---|---|---|---|

## 规则

- 用户用自然语言描述需求时，先记 S-xxx，保存原话；不要改写。原话是需求的来源和边界。
- S 记录必须有说话人、日期和状态；状态只用“已记录 / 已废弃”。被新陈述取代时，旧 S 标“已废弃”，不删除。
- Q 是缺口问题，不是需求来源。问题必须具体、开放、可回答；不要用“是否还需要别的”这类空问题。
- Q 的“依据”必填：`S-` 用户原话、`Q-` 其他问题、`D-` 决策、`R-` 文档或 `P-` 实践参考。依据要写清触发缺口的检查项和缺失内容。
- Q 的“确认人”必填：按 `team.md` 和模块负责人提议，无法判断时问用户；AI 不编姓名。
- Q 被回答后，把回答内容另记为 S-xxx；Q 的“回答”列写“见 S-xxx”，不要把 Q 本身当作来源。
- 故事卡的来源只写 `S-/D-/R-`，不写 Q。Q 是问题，不是出处。
- “没反对”不算确认。批量确认必须写明编号范围，例如“Q-001 至 Q-005 确认”。
- 记录回答人姓名和日期；回答尽量保留原话，转述需标注“转述”。
- 回答人必须是姓名；只知道角色时写“待确认（角色）”，不按已确认处理。
- Q 确认后，稳定的业务事实回填 `context.md`，术语回填 `glossary.md`。
- S 和 Q 分别按顺序编号，不复用、不跳号。
- `P` 只能生成 Q，不能作为来源；`I` 不能进入“已确认”。
- 设计细节不是需求缺口；进 `DSN-`。
- AI 只能记录确认，不能代替人确认。
