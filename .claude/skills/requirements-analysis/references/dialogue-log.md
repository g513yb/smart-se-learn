# 对话记录

S = 用户自己发起、能脱离 AI 文本独立成立的产品或需求陈述，是需求来源。角色输入写入 `personas.md`，团队输入写入 `docs/team.md`，状态由 AI 维护，均不记 S；人对 AI 的提问不进 S；简短确认、仅依赖问题的答复、AI 草案的采用/确认，以及对 AI 草案/建议的纠正、改写不记 S。
Q = 缺口问题，不是来源；回答写入 Q 的回答列，补充新内容时才另记 S。

本文中的编号和内容均为通用示例，不对应本项目。

## 用户原话（S）

| 编号 | 原话 | 状态 | 关联需求/问题 |
|---|---|---|---|
| S-001 | 示例：用户可以导出自己的数据。 | 已记录 | Q-001 |

状态：已记录 / 已废弃

## 缺口问题（Q）

| 编号 | 问题 | 依据 | 状态 | 回答 | 关联需求 |
|---|---|---|---|---|---|
| Q-001 | 示例：“导出”指什么？ | S-001 | 待回答 | | |

状态：待回答 / 部分回答 / 已确认 / 已废弃

## 规则

- S 只收用户自己发起、能脱离 AI 文本独立成立的产品或需求陈述；角色输入写入 `personas.md`，团队输入写入 `docs/team.md`，状态由 AI 维护，均不记 S；人对 AI 的提问不进 S；简短确认、仅依赖问题的答复和 AI 草案的采用/确认不记 S，记入 Q 的回答列；对 AI 草案/建议的纠正、改写也不记 S，改正后的内容直接写入目标文件。
- 用户用自然语言描述需求时，先记 S-xxx，保存原话；不要改写。原话是需求的来源和边界。
- S 的状态只用“已记录 / 已废弃”。被新陈述取代时，旧 S 标“已废弃”，不删除。
- Q 是缺口问题，不是需求来源。问题必须具体、开放、可回答；不要用“是否还需要别的”这类空问题。
- Q 的“依据”必填：`S-` 用户原话、`Q-` 其他问题、`D-` 决策、已写入文件/用户提供的文档或 `P-` 实践参考。依据要写清触发缺口的检查项和缺失内容。
- Q 不设回答人、日期字段；用户用自己的话回答 → 把回答原文写入 Q 的“回答”列；回答本身补充了新内容时才另记 S-xxx，回答列写“见 S-xxx”；简短确认不记 S；人采用 AI 草案 → 不记 S，写“已采用 AI 草案，见目标文件”；多条 S 回答时写“见 S-xxx、S-yyy”。
- 故事卡的来源只写 `S-/D-`，不写 Q。Q 是问题，不是出处。
- “没反对”不算确认。批量确认必须写明编号范围，例如“Q-001 至 Q-005 确认”。
- Q 确认后，稳定的业务事实回填 `context.md`，术语回填 `glossary.md`。
- 故事写成后，把相关 Q 的“关联需求”改为对应的 `REQ-xxx`；一条 Q 影响多个 REQ 时列全；无法唯一对应时写模块缩写（如 `DIAG`）并注明“模块级”；故事写成前写“待建”，故事写成后不得保留“待建”。
- S 生成 Q 后，把 Q 编号写入 S 的“关联需求/问题”列；未生成 Q 时写对应文件（如 `vision.md`）或模块缩写；没有对应项写“无”；Q 回填 `REQ-xxx` 后，S 保持 Q 编号，不重复填 REQ；不得保留“待建”。
- 多个待答 Q 的处理顺序：确定冲突的 Q 优先；其次可能冲突/无法判断的 Q；其余普通缺口 Q 按 `vision.md` 范围节的模块顺序，再按 Q 编号升序；同一层内一次只处理一个 Q。
- `dialogue.md` 顶部维护“待答 Q 索引”：编号、模块、一句话、类别（确定冲突/可能冲突/普通）、建议顺序；Q 新增、回答或废弃后同步；无待答 Q 时写“无”。
- 新增或更新 Q 后，同步 `coverage-scan.md`：对应模块的维度聚合和模块覆盖总览改为“已问待答”；没有对应维度时写入该模块的“清单外建议”。
- S 和 Q 分别按顺序编号，不复用；正常追加不跳号。误记的非陈述型答复移出 S 表后，原编号作废、不分配给新条目，允许空号。
- `P` 可以生成 Q，也可以支撑 AI 草案；`P` 不能作为最终来源；推断不能进入“已确认”，需要保留时写 Q 或标为“AI 提议”。
- 设计细节不是需求缺口；进 `DSN-`。
- AI 只能记录确认，不能代替人确认。

## S 的收录标准

记录前先做独立陈述测试：

> 脱离当前问题，这句话还能独立表达需求、事实或决定吗？

- 只有产品或需求陈述记 S：愿景、范围、非目标、约束、功能需求、产品行为。
- 角色定义、目标、场景、痛点、关系不记 S，写入 `personas.md`。
- 团队成员、分工不记 S，写入 `docs/team.md`。
- 当前阶段、下一步不记 S，由 AI 按阶段表维护 `STATUS.md`。
- 能，且属于产品或需求陈述 → 记 S，保存原话。
- 拆分 S 时，每个 S 必须能独立成立；不能拆出依赖前句的片段。
- 只是选择、确认或复述问题中的选项 → 写入 Q 的“回答”列，不记 S。
- 纯确认（“是 / 可以 / 对 / 嗯”）→ 写入 Q 的“回答”列，不记 S。
- 回答本身是独立、有内容的产品或需求陈述 → 写入 Q 的“回答”列，并可另记 S。
- 对 AI 草案的采纳 → 不记 S，写“已采用 AI 草案，见目标文件”。
- 对 AI 草案、分析或建议的纠正、改写、措辞调整 → 不记 S；把改正后的内容写入目标文件。

通用示例（非本项目）：

| 用户说 | 处理 |
|---|---|
| 用户可以按标签筛选记录 | 记 S |
| 使用者第一次使用时先导入论文（角色场景） | 不记 S；写入角色卡 |
| 团队成员是张三、李四（团队信息） | 不记 S；写入 `team.md` |
| 是 / 可以 | 不记 S；写入 Q 的回答列 |
| 只支持 PDF（回答“支持哪些格式”） | 不记 S；写入 Q 的回答列 |
| 记录一词不对，应该是记笔记（纠正 AI 草案） | 不记 S；改正后的内容写入目标文件 |
| 我补充一下：导出只给教师用 | 记 S；Q 的回答列写“见 S-xxx” |

## 多个 S/Q 对应同一需求

- 同一 `REQ` 可以由多条 S 和 Q 支持；S 的“关联需求/问题”、Q 的“关联需求”可以写多个编号，用顿号分隔。
- 一条 Q 可以由多条 S 回答；Q 的“回答”列写回答原文、“见 S-xxx、S-yyy”，或“已采用 AI 草案，见目标文件”。简短确认只写回答原文，不记 S。
- Q 状态：待回答 / 部分回答 / 已确认 / 已废弃。只有人确认“答完了”，才能标“已确认”。
- Q 太宽、需要多个方面回答时，拆成多条 Q；每条独立跟踪状态和关联需求。
- 需求写入 backlog 前，所有关联到它的 Q 必须是“已确认”或“已废弃”；存在“待回答/部分回答” → 不写入。
- 一条 Q 影响多个需求：各需求的答案可能不同 → 拆 Q；答案相同 → 可写多个 `REQ`。
- 一条 S 改变时：检查同一需求的其他 S/Q；仍能支持 → 需求保留并更新；不能支持 → 更新、拆分或废弃，由人决定。
- 需求 ID 合并、拆分、改名时：更新所有 S/Q 的关联；旧 ID 只在需要追溯时写在备注。

## S 矛盾处理

### 1. 优先级

发现 S 前后矛盾时，暂停当前的提取、提问和写文件，先处理矛盾；矛盾未解决前，不继续依赖该 S 的内容。

### 2. 判定

同一主体、同一属性、不同结论 → 矛盾候选。补充细节、增加条件、细化措辞不算矛盾，按兼容补充或澄清处理。

### 3. 展示与选择

列出旧 S、新 S、矛盾点，请人选择：

1. 新陈述取代旧陈述
2. 旧陈述是例外
3. 两者在不同条件下都成立
4. 新陈述需要修正
5. 暂不处理

AI 不替人选择。

### 4. 影响分析

修改 S 前，先分析影响。必须逐文件检查，不能只查 backlog。

| 文件 | 检查什么 |
|---|---|
| `vision.md` | 项目定位、目标、范围、非目标、成功标准、关键约束 |
| `personas.md` | 角色定义、目标、典型场景、痛点与约束、角色关系 |
| `context.md` | 稳定业务事实 |
| `glossary.md` | 术语定义、别名、模块缩写 |
| `backlog.md` | 故事、验收标准、优先级、负责人、依赖 |
| `nfr.md` | ID、类别、指标、场景与边界 |
| `models/` | 图元素、状态、流程、模型来源 |
| `design-notes.md` | DSN 的假设、适用阶段、备注 |
| `decisions.md` | 基于旧 S 的决策 D |
| `coverage-scan.md` | 覆盖状态、关联 Q |
| `dialogue.md` | 其他 S/Q、关联列 |
| `research/` | 外部证据不修改；与 S 冲突时写 Q |

规则：

- 从 S 的“关联需求/问题”列出直接关联的 `REQ`/`Q`。
- 逐文件检索与旧 S 内容相关的条目，列为候选。
- 每个文件都要给出结论：受影响 / 不受影响 / 无相关条目 / 无法判断；不能跳过。
- 每个候选写依据：旧 S 说什么、该条目写什么、为什么受影响。
- 无法判断写 Q，不直接改文件。
- 只有人确认的条目才更新。
- `decisions.md` 中的 D 不直接修改；只标记“可能受影响”，由人决定是否作废旧 D、新建 D。
- `research/` 是外部证据，不因 S 改变而修改；如果 S 与 P 观察冲突，写 Q。
- `design-notes.md` 的 DSN 如果假设失效，标注或更新，由人确认。
- 影响分析保证“所有文件都被检查”，不保证语义上穷尽；AI 不得声称“已覆盖全部影响”。

### 5. 记录方式

- **新陈述取代旧陈述**：旧 S 状态改“已废弃”；新 S 关联列写“取代 S-xxx”；旧 S 保留。
- **旧陈述是例外**：两条 S 保留；在关联列写“例外”；检查相关文件是否补例外条件。
- **两者在不同条件下都成立**：两条 S 保留；写明适用条件；检查相关文件是否补条件。
- **新陈述需要修正**：不改旧 S；请人给出修正后的陈述，记为新的 S。
- **暂不处理**：写 Q“S-xxx 与 S-yyy 冲突，哪条为准？”；两条 S 保留；Q 回答前不把矛盾内容写入其他文件。
