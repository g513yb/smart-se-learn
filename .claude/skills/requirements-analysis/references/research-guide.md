# 调研指南

同类产品拆解为主，标准、学术、开源只在解释不了的地方补位。

## Brief 的时机

- 来源登记提前：有哪些、是否官方、是否可达，维护在 `sources/INDEX.md`
- 正式 brief 在模块进入分析前完成：它是 AI 主动发现需求的依据；没有本模块 brief 或快速调研，不得主动提出 P 驱动的需求候选
- 不要为所有模块提前写 brief；按模块或迭代做，时间盒 30～60 分钟

## 快速调研

适用：AI 准备提出遗漏内容，但不确定，需要参考类似项目或功能。

- 不要求 1.0 通过；可以在 1.0 前或对话中按需使用。
- 查 1～2 个已批准或部分验证来源，不写完整 brief。
- 输出：
  1. P 观察（用户可见行为，标 P-ID 和证据强度）；
  2. Q（每条观察转成问题）；
  3. 可选 AI 草案，标“AI 提议”。
- AI 草案必须人确认后写入；P 不是最终来源。
- 快速调研不替模块边界、范围或优先级做决定；这些仍由 1.0/人确认。
- 快速调研的结论只是线索，不作为事实性结论；需要系统分析时，回到正式 1a brief。

## 输入

| 输入 | 来源 | 缺失时 |
|---|---|---|
| 模块边界 | 1.0 已通过 | 不写 brief |
| 检索问题 | 模块 + 六维之一 | 先写问题 |
| 已批准来源 | `sources/INDEX.md` | 报告，不做 P 驱动 |
| 范围卡 | 本文件 | 未填不检索 |

## 选择对标

- 一个模块可以有一份综合 brief，按来源分节；也可以每个平台一份，最后由矩阵汇总。
- 按模块找 1～2 个，不追求一个全能平台。
- 优先：同用户群、同智能能力、有公开文档或演示、成熟产品。
- 研究型模块找不到成熟商业产品时，用论文原型和学术综述。

## 信息渠道

| 优先级 | 渠道 |
|---|---|
| 高 | 官方帮助中心、用户手册、API 文档、演示视频、更新日志 |
| 中 | 公开案例、产品评测、G2/Capterra（只作线索） |
| 低 | 博客、营销页、AI 生成内容（只作线索） |
| 补充 | 标准文档、同行评议论文、成熟开源项目文档 |

## 检索

- 先写检索问题，绑定模块和六维之一。
- 中英文同义词扩展。
- 查用户能力，不查架构：用 features、help center、user guide；不用 architecture、tech stack、implementation。
- 事实性主张至少两个独立来源。

## 提取

每条观察分三层：

1. 用户问题/价值
2. 用户可见行为 → 需求候选，转 Q
3. 实现方式 → 设计线索，转 `DSN-`，不进需求

写成“用户能……，以便……”，不写“系统采用……”。

## 执行步骤

1. 填范围卡：模块、检索问题、维度、平台（从已批准清单选 1～2 个）、来源等级、明确不搜、停止条件。
2. 查来源登记：P-ID、标题、机构/作者、年份、URL 或文件、访问日期、状态。
3. 只读已批准和部分验证来源；候选需用户批准；排除来源不用。
4. 提取用户可见行为：写“用户能……，以便……”或“用户看到……”；不写架构、算法、数据模型、技术栈。
5. 每条观察标 P-ID 和证据强度（全文 / 摘要 / 页面级 / 视频）。
6. 写差异：哪些不适用、为什么；来源覆盖不足在哪里。
7. 生成 Q：每条带 P 依据和具体缺口；不写需求。
8. 过完整性检查，写 brief。

## Brief 模板

`docs/requirements/research/<平台>.md` 或模块综合 brief `<模块>.md`：

1. 检索问题
2. 来源清单：`P-ID | 标题 | 机构/作者 | 年份 | URL | 访问日期 | 类型 | 状态 | 证据强度`
3. 需求观察（用户可见行为）
4. 设计线索（转 `DSN-`）
5. 与本项目的差异（不适用项及原因）
6. 生成的 Q

模块综合 brief 按来源分节，但六段必须齐全。

## Brief 完整性检查

- [ ] 六段齐全：检索问题、来源清单、需求观察、设计线索、差异、Q
- [ ] 每条观察有 P 编号和证据强度
- [ ] 观察只写用户可见行为，没有架构、算法、数据模型或技术栈
- [ ] 设计线索都在 `DSN-`，没有混进观察或 Q
- [ ] 没有把 P 写成需求、验收标准或优先级
- [ ] 差异写明不适用项和原因
- [ ] Q 都有 P 依据和具体缺口
- [ ] 来源状态已记录；候选和排除来源没有混入
- [ ] 停止条件已满足

## 停止条件

- 新增问题枯竭
- 达到 1～2 个平台、3～5 个来源、30～60 分钟
- 没有已批准来源：停止，报告并请用户提供材料
- 来源冲突：记录双方，生成 Q，不选边
- 模块边界不清：不写 brief

## 规则

- `P` 可以生成 Q，也可以作为 AI 草案的依据；`P` 不是最终来源，最终内容必须人确认。
- 引用 `P` 的最终需求必须另有 S/D、已写入文件或人确认。
- 候选来源需用户批准；排除来源不写入 brief。
- 来源冲突不选边；记录双方并生成 Q。
- Brief 不是需求文档；不得写成需求、验收标准或优先级。
- 竞品有 ≠ 我们要；分析它没做什么同样重要。
- 不整段复制，注意许可。
- 每个模块先做 30～60 分钟，新增问题枯竭就停。
- 不把项目内部数据发到搜索。
